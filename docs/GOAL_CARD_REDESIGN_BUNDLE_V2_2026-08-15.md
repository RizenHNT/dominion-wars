# 卡牌回炉修规格 — bundle_v2（540 张保持规模）

> 背景: 2026-08-15 卡牌策划交付 3 套互相不一致的全卡（V1 文档 120 张语义卡 / bundle.json 600 张 / bundle_v2.json 540 张）。PL 审查后，人类拍板 **B 路线：bundle_v2 回炉修（补类型 + 去重名 + 语义化命名），保持 540 张规模**。

> 参考基准（策划手上的既有资产）: `docs/CARD_DESIGN_V1_2026-08-15.md`（类型分布/语义命名/卡组模板的最优参考）、`docs/CARD_DESIGN_MODEL_2026-08-15.md`（设计宪法）、`data/schema/cards.schema.json`（字段权威）、`data/cards/*.json`（引擎落地格式）。

## 一、为什么回炉修（PL 审查铁证）

bundle_v2.json 目前是**模板批量复制产物，不合格**，客观证据：

1. **类型结构塌方**：544 张 = 536 随从 + 4 统领 + 4 空 type。**零 SPELL / AMBUSH / PUNISH**（schema 枚举明确支持四类，V1 文档每阵营都有咒文/伏击/惩罚）。
2. **重名泛滥**：79 组重名全部 x8，**544 张全部落在重名组**（`flame_m001`~`flame_x060` 模板复制铁证）。同 id 前缀、同名卡片内容却不同（如同名"爆裂冲击"有多张不同 P/stat 的卡）。
3. **名实不符**：咒文名卡是随从（"爆裂冲击"是 1/2 白板随从、"火雨之雨"是随从）；`main` 用 active/eff 混用、`supplement` 用 eff+over、无阵营用 eff 无 active——字段不一致。
4. **id 无语义**：`flame_m001`/`flame_x060` 模板编号，不是 V1 的 `flame_bolt` 语义 id。
5. **README 自夸与数据矛盾**：README 自称"v10 自查全部通过"，但类型/重名/语义三项实际全塌——自查维度缺这 3 项。
6. **与引擎 schema 字段不对齐**：bundle_v2 用中文 `type:"随从"`、`stat:"8/8"`、`kw:"突袭"`；引擎落地格式是英文枚举 `type:"MINION"`、数字 `attack/health`、数组 `keywords`（见 `data/cards/neutral.json`）。

## 二、修复目标（保持 540 张规模）

- **总量不变**：540 张（4 阵营 × 120 [60 main + 60 supplement] + 无阵营 60 [main]）。统领另计（见 §五）。
- **结构对齐**：每张卡四要素齐全——类型、唯一名、语义 id、字段对齐 schema。

---

## 三、类型配额（从 536 随从中转出咒文/伏击/惩罚）

参考 V1 文档的类型分布比例，把随从堆里转出三类型。**建议每阵营配额**（策划可 ±10% 微调，但五类都必须存在且数量合理）：

| 阵营 | 总张数 | 随从 | 咒文 SPELL | 伏击 AMBUSH | 惩罚 PUNISH |
|---|---|---|---|---|---|
| 烈焰帝国 | 120 | ~64 | ~32 | ~12 | ~12 |
| 机械遗迹 | 120 | ~62 | ~34 | ~12 | ~12 |
| 深海联盟 | 120 | ~62 | ~32 | ~13 | ~13 |
| 古木圣地 | 120 | ~58 | ~36 | ~13 | ~13 |
| 无阵营 | 60 | ~30 | ~16 | ~7 | ~7 |

> 参考 V1 实际分布（烈焰 16随+6咒+2伏+1惩；机械 12+10+2+2；深海 12+8+2+3；古木 10+11+3+4；中立 6+3+1+2）。上表按 120 张/阵营等比放大，策划可结合阵营主题微调（如机械多咒文引擎、古木多惩罚）。

**硬性要求**：
- 每个阵营（含无阵营）**至少**：咒文 ≥ 10、伏击 ≥ 5、惩罚 ≥ 5。
- 咒文/伏击/惩罚的**效果语义必须符合类型**（咒文=一次性施放、伏击=盖放触发、惩罚=响应对手行动）。禁止再用"咒文名给随从"式名实不符。
- 保留 4 阵营的 pace/win 主题方向（烈焰=快攻破城 / 机械=下载轴 / 深海=弃牌潮位 / 古木=生命≥512）。

## 四、命名与字段修复

### 4.1 语义化命名（名实相符）
- **id**：`flame_m001` → `flame_bolt` 式语义 snake_case（参考 V1 的 `flame_bolt`/`machine_alpha`）。前缀 = 阵营（flame/machine/sea/wood/neutral_）。
- **name**：中文卡名必须反映效果/身份。禁止"白板随从叫爆裂冲击""咒文名给随从"。
- **唯一性**：**0 重名**（全 540 张 id + name 各自唯一）。

### 4.2 字段对齐 schema（权威 = `data/schema/cards.schema.json` + `data/cards/*.json`）
- `type`：英文枚举 `MINION` / `SPELL` / `AMBUSH` / `PUNISH`（不是中文"随从"）。
- 身材：数字 `attack` / `health`（不是字符串 `stat:"8/8"`）。
- 关键词：数组 `keywords`（`嘲讽/圣盾/扰魔/突袭`，不是字符串 `kw`）。
- 效果字段：按类型给结构化效果（`text` 为面向玩家的展示文本；效果语义入 effect 结构）。具体字段名对齐 schema `$defs`。
- `faction`：5 枚举（烈焰帝国/机械遗迹/深海联盟/古木圣地/无阵营）。

---

## 五、统领（4 张，独立段）

bundle_v2 现有 4 统领（flame/wood/sea/machine_leader）用纯中文文本字段（win/active/punish）。**统领重设计已是独立批次**（mailbox 统领机制三裁决：全量重设计 → DeepSeek 策划）。本回炉修**只要求结构对齐**，不重新设计效果：
- 统领结构改为 `leader:true + leaderDef`（对齐 `data/cards/neutral.json` 的 `shadow_of_fate` 结构）。
- `leaderDef.winCondition` 用 schema 枚举（`ROYAL_CASTLE_BREAK` / `GIANT_HEALTH_GE` / `OPP_DISCARD_TOTAL_GE` / 下载轴等）。
- 4 统领效果文本保留，待重设计批次替换；本批次不动平衡。

## 六、自查清单（必须可复验，不能口头声称）

策划交付时必须附**脚本可查证**的自查结果：
1. **类型分布**：全卡 type 计数（四类 + 统领），每阵营 ≥ 下限。
2. **唯一性**：全卡 id 唯一、name 唯一（0 重复）。
3. **schema 校验**：所有卡通过 `data/schema/cards.schema.json`（如已有校验脚本则跑；没有则说明用了哪些字段与 schema 对齐）。
4. **名实相符抽查**：随机抽 10 张，卡名能反映效果身份（附抽卡清单）。
5. **README 更新**：v2 README 的自查声明改为"按 §六 清单通过"，删除"v10 全过"这类不可复验声明。
