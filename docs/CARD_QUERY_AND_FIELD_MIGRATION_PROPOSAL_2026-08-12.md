# 卡牌检索与字段分层提案

> 状态：技术/设计讨论稿，不是已批准的 schema 变更。本文件不改变现有卡牌行为。

## 1. 当前问题

现在 `tags` 同时承担了三种职责：

1. 显示卡牌主题，例如“龙”“魔像”“仪式”；
2. 让效果寻找一类卡牌；
3. Java `tagsFree` 将同名 tag 变成每回合一次的使用限制。

这会导致一个直观问题：给卡牌加一个“龙”标签，可能不只是方便检索，还会意外影响它能否出牌。当前 91 张卡使用了 61 种 tag，其中只有少数 tag 重复较多，说明它们混合了种族、策略主题、效果主题和统领标记。

当前数据已经能看到这种耦合的实际影响：深海牌组中“巨兽”和“弃牌”各有两张卡，古木牌组中“恢复”“精灵”“野兽”“树灵”“结界”“荆棘”各有两张卡。按现行 `tagsFree` 规则，同组卡牌会互相消耗本回合的使用机会；这可能是有意的节奏设计，也可能让玩家误以为它们只是普通分类。

## 2. 推荐的字段分层

未来不直接删除 `tags`，而是逐步引入更明确的字段：

| 字段 | 作用 | 是否直接改变规则 |
|---|---|---|
| `id` | 精确指定一张卡 | 否，作为稳定身份 |
| `cardFamilyId` | 原版、强化版、重印版共享身份 | 否，供检索和星位兼容 |
| `faction` | 阵营和组牌限制 | 是，影响构筑合法性 |
| `tribes` | 龙、魔像、树灵等身份分类 | 通常否，供效果检索 |
| `keywords` | 嘲讽、圣盾、扰魔等内置规则 | 是，直接改变规则 |
| `archetypes` | 星位、速攻、弃牌等构筑主题 | 通常否，供支援卡和 UI 检索 |
| `abilityTags` | 破坏、恢复、抽牌等效果主题 | 通常否，供检索、展示和测试 |
| `usageGroup` | 每回合一次的限制组 | 是，替代 `tagsFree` 的隐式规则 |
| `text` | 给玩家看的说明文字 | 否，不能成为唯一规则来源 |

其中 `tribes`、`archetypes`、`abilityTags` 都可以是数组，但必须有不同命名空间，不能再全部塞进一个自由文本数组。

## 3. 检索范围采用四档，不做任意查询语言

卡牌效果和星位条件建议只允许四种稳定检索方式：

1. **精确卡牌**：`cardId = flame_star_observer`。最严格，适合传说星位和指定组件。
2. **卡牌系列**：`cardFamilyId = flame_star_observer`。允许补充包推出强化版继续满足旧条件。
3. **身份/主题**：阵营、种族、类型、关键词或构筑主题。适合普通支援卡。
4. **当前状态**：在场、受伤、位于某位置、已被保护等。只由专门的状态选择器负责。

不建议让卡牌 JSON 直接写任意表达式查询。这样短期灵活，长期会让 Java、C#、AI 和 UI 各自解释一套规则。

## 4. 星位如何使用这套分层

星位可以按难度选择不同精度：

- 普通星位：要求阵营/种族/主题组合；
- 高难度星位：要求 `cardFamilyId`；
- 传说星位：要求精确 `id`、指定位置和保护条件；
- 强化卡：通过 `cardFamilyId` 兼容旧星位，或用新 `id` 设计更严格的新星位。

这样既保留“指定卡名增加构筑难度”的特色，也不会让所有后续加强卡都必须复制旧卡名。

## 5. `tags` 的迁移策略

当前先保留 `tags`，不改旧卡，不改变 Java 行为。正式迁移时建议分三步：

1. 给现有 tag 做一次归类：种族、主题、效果、显示标签或使用限制；
2. 将真正的每回合限制搬到 `usageGroup`，让 `Game` 读取明确字段；
3. `tags` 暂时保留为兼容/显示字段，待所有卡和测试迁移后，再决定是否废弃。

在迁移完成前，不能把 `tags` 当成纯显示字段，也不能随意给新卡增加会被 `tagsFree` 读取的 tag。

## 6. 当前不实施的内容

- 不现在修改 schema；
- 不给 91 张现有卡批量重分类；
- 不把星位字段提前加入生产数据；
- 不改变现有 `tagsFree` 的 Java 行为；
- 不把 `text` 改成自动生成；
- 不实现任意组合查询语言。

正式实施前，需要 PL/人类负责人确认：`tags` 的每回合限制是否是正式设计，以及 `tribes`、`archetypes`、`abilityTags` 是否采用这套分层。
