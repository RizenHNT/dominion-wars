## 0. 本版要解决的三件事

### 0.1 旧卡表的实测缺陷（依据 `PL_CARD_YARDSTICK_2026-09-12.md` §2.2）

只消融效果（同类型、同身材、仅去效果）后的读数：

| 阵营 | 效果推轴的卡 | 效果**零贡献**的卡 | 效果**拖累**轴的卡 |
|---|---|---|---|
| 深海 | 7 | **10** | 3（噪声级） |
| 古木 | 7 | 7 | **4** |
| 机械 | 1 | **12** | 6（噪声级） |

**一半以上的卡，其效果对胜利轴没有任何贡献。** 这是 v2 必须修掉的核心问题。

### 0.2 字段缺失（必须在 v2 补齐）

- `machine_golem` 卡面写"嘲讽"，JSON **既无 `keywords` 也无 `guard`** → 实际没有嘲讽。
- `machine_factory` 是**没有任何效果**的咒文（`chantEffects` 里只有召唤，但整卡设计目的不明）。
- `machine_assembler`：`punishActivatable: true` + `punishCost: 0` + `punishCondition: "ALWAYS"` 但 `punishEffects: []` → **可激活的空惩罚**。
- `machine_assembler` 用 `pushEffects` 表达"上传时抽1"，需确认引擎是否读该字段（见 §5）。
- 古木 4 张卡的 `param` 全是 `root`/`rampant`，**没有任何普通（无增幅）强化卡** → 机制部件缺失。

### 0.3 发动条件缺失

owner 要求："高收益卡牌上我希望最好有些发动条件"。v2 的规则是：
**凡是收益超过现有顶级卡的卡，必须带一条可验证的发动条件**，写成"若 xxx，则【字段】"。

## 1. 设计总则

1. **每张卡必须能回答"它推进胜利轴的哪一步"** —— 答不上来就不占槽位（§0.1 的直接对策）。
2. **每套卡组必须有 2 条以上互相制约的路线**，否则不叫策略深度：
   - 一条**主胜利轴**（低风险、慢）
   - 一条**爆发轴**（高收益、需条件、可被打断）
   - 一条**防守轴**（保住主轴的载体不被拆）
3. **身材定价**：不靠身材堆叠。1 费 = 1/1 或 2/1 带小效果；高身材必须配高惩罚值。
4. **惩罚值是唯一的代价轴**（本游戏没有法力费）。所以：
   - 低惩罚卡 = 低收益
   - 高收益卡 = 高惩罚 **或** 带发动条件
5. **卡组规模**：沿用 **20 种 × 3 张 = 60 张**（与现有 `data/decks/*.json` 一致，不改抽牌压力与牌库循环计数）。
6. **不改胜利条件、不改阈值、不加第二胜利轴**。

### 2.2 为什么现有古木只能到 85.3/局（差 6 倍）

不是公式不够强 —— 公式**够强**：

```
疯长满 3 层（×8），扎根 14 层时，一张「基础 4」的强化卡 = (4+14)×8 = +144 生命
一张「基础 6」的强化卡 = (6+14)×8 = +160 生命
```

**512 ≈ 4 张这样的卡打在同一个封印单位上。** 差 6 倍的原因是**卡池问题**：

- 古木 BUFF 卡的 `base` **最大只有 2**（`wood_guard/druid/bear/treant/warden/stag/owl/growth` 全是 `amount: 2`）
- 扎根卡够多（10 个 `ADD_ROOT` 各 +2 = 可能 +32 层），但**种子卡只有 3 张**（sapling/wisp/guard 之外全靠它们）
- 而 **7 张古木卡的效果对轴零贡献**（`bark/circle/renew/root/veil/moon/spring`）—— 它们是纯粹的防守/解场牌，占了 7/20 槽位
- 4 张卡的效果**在拖累轴**（`wisp +10.0`、`thorn +9.2`、`owl +4.9`、`stag +4.1`）

⇒ **结论：把"铺种子"和"喂大"做成两条明确的引擎，并把防守牌压到 4 张以内，512 是可及的。**

### 2.4 古木的 512 路径（把数字算给 owner 看）

```
目标：一个封印单位生命 ≥ 512

早期：（铺种子）sapling/wisp/guard/druid/bear/treant/warden/stag → 每张扎根 2~3
      ⇒ 一场对局可累积扎根 ~20 层（10 个种子来源 × 3 张）

中期：（疯长）wood_growth ×2~3，或统领惩罚降临 → 疯长 3（上限，×8）

爆发：扎根 14、疯长 3 时
      wood_bloom  (6+14)×8 = +160
      wood_eternal(4+14)×8 = +144
      普通 buff   (2+14)×8 = +128
      ⇒ 第 1 张 160 + 第 2 张 144 + 第 3 张 128 + 第 4 张 ~112 = 544 ≥ 512 ✅
```

**关键洞察（设计要点）**：因为 `punk=root` 的强化卡**同时加扎根层数**，所以**每张强化卡比上一张更大** —— 这是一个**递增加速**轴，而不是线性的。这正好匹配"后期卡组"的身份。
**代价**：每张卡都要把对手的惩罚值堆起来（`wood_bloom` 4 费、`wood_eternal` 5 费），而**惩罚值就是对手的手牌** ⇒ 对手会变得更难对付。**这才是古木真正的平衡阀门**，不需要额外削弱。

## 3. 机械遗迹 —— "成长，前期上传，提交/上传收益，后期统领+下载爆发，怪兽全 1 费 1/1，靠回滚控制云端栈顶"

### 3.1 机制现状（已核实）

| 事实 | 证据 |
|---|---|
| 出牌惩罚值 = 0，`commitCost`/`uploadCost`/`downloadCost` 是**生命周期动作的惩罚抽牌数** | `RULES.md §12.4` |
| **下载必须有载体**：己方场上 tag="机械" 的单位；**机械统领地标本身也是合法载体** | `RULES.md §12.4` |
| 地标层数 = 本局已发起下载次数；第 2 层 → 吟唱1 → 摧毁地标 → 召唤 `machine_alpha` | `RULES.md §12.4` |
| **只能下载云端栈顶**，不能跳层 | `RULES.md §12.4` |
| **回滚**：主动动作，队列卡回手，**不产生惩罚抽牌**，提交时已结算的效果不撤销 | `RULES.md §12.4` |
| 胜利：累计下载 6 次 | `machine.json` `leaderDef.winParam: 6` |

### 3.2 机械的真问题（实测）

**所有机械卡的效果对下载轴的贡献加起来不到 0.15/局，而基线是 4.6/局**（`PL_CARD_YARDSTICK §2.2`）。
⇒ **机械的下载推进来自默认机制**（载体 + `downloadCost 1` + 地标），**卡牌效果几乎没用**。
⇒ 所以机械卡表的设计目标**不是**"加效果强的牌"，而是三件事：
1. **保证载体永远在场**（载体没了就不能下载）
2. **把 `downloadCost` 压低**（每次下载的惩罚值）
3. **控制栈顶顺序**（回滚 + 上传顺序）

## 6.1 ⚠ `guard` 不是纯风味改动 —— 它可能**堵死所有对局**

**已核实的语义**（`AttackTargetPolicy.cs:126-142` + `:74-80`）：
`guard: true` 的统领，在**该玩家场上还有任何存活非统领随从**时，**不能被选为攻击目标**。

**风险**：`win.enemy_leader_defeated` 是 **7/16 最常见的结束方式**。如果给三个统领都加上 `guard`：
- 打统领的路径几乎关闭（古木/机械的场面通常一直有小怪）
- 而**胜利条件本身没有变**（古木仍需 512 封印生命、机械仍需 6 次下载、深海仍需 18 弃牌）
- ⇒ 很可能出现**双方都到不了自己的阈值、也斩不掉对方统领**的僵局

**所以这条不能单独决定。** 需要 owner 在下面两条里选一条一起批：
- **(a) 只给部分统领 `guard`**（例如只给耐久 8 的机械地标，不给耐久 20 的木统领），把"斩首"保留为对高耐久统领的正当解法；
- **(b) 给全部统领 `guard`，同时接受"对局变长"**，并把僵局风险交由 §7 的 L3/L6 多轮测试量化（若僵局率显著上升，我会回来报告而不是自行放宽阈值）。

## 6.2 已核实的引擎事实（子代理审计，file:line 证据）

**好消息（这套机制比我想的更能用）**：
- **每种效果列表都真的有效**：`onPlayEffects`、`enterEffects`、`punishEffects`、`chantEffects`、`ambushEffects`、`commitEffects`、`pushEffects`、`pullEffects` **全部被引擎读取**（`pushEffects` 读在 `EffectRuntime.Mechanical.cs:144-149`）。所以 `machine_assembler` 与 `machine_recycler` 的写法**都是对的**。
- **卡级 `condition` 字段真的会拦截效果**：`EffectDispatcher.cs:131-138`，在效果结算前检查；未知词条**安全地不结算**。
- **条件是"每张效果"粒度**，可以是任意整数（`HAND_GE_7` 也行），且**正式卡牌里零张卡用过** ⇒ 全新可用空间。

**坏消息（必须让 owner 知道）**：
1. **`onDeathEffects`（"死亡时触发"/同归）这个字段根本不存在** —— 引擎、schema、数据里都没有。"同归"关键词也在 9 个"无行为关键词"里。**今天写不了亡语卡。**
2. **15 个合法关键词里只有 4 个有引擎行为**：嘲讽、突袭、扰魔、圣盾。其余 11 个（潜行/吸血/同归/献祭/复活/秒杀/震慑/沉默/占星/寄生/降临）**写了也是装饰**。
3. **`chant > 0` 的卡永远不结算 `onPlayEffects`**（`PlayCardActionHandler.cs:309-312`）—— 吟唱卡的主效果必须写在 `chantEffects` 里。
4. **古木来源的 buff 用 `param:"atk"` 会变成攻击清零**：因为成长一旦触发就 `Sealed`，而 `Sealed` 把攻击置 0（`Combat.cs:183` 先设攻击、`:195` 再清零）。**想要纯攻击 buff 的古木卡，必须避免成长**。
5. **`machine_golem` 卡面写的"嘲讽"是假的**（`machine.json:143` 有文字、无 `keywords`）。全卡池**只有它一张**是这种"文字有、数据无"。
6. **`machine_recycler` 的 `ROLLBACK 1` 回滚的是它自己**（`CommitActionHandler.cs:107` 把 `selectedTargetId` 钉成正在提交的那张），所以卡面"队列中的一张卡"在队列只有它自己时不成立。**这是既有缺陷，v2 需要改卡面或改行为。**

### 9.2 为什么这套能到 512（前期铺垫正是条件要求的）

```
门槛      需要做到什么                     放开哪张卡
扎根≥1    打出一张扎根卡（新芽树灵即可）      年轮 抽2  → 加速抽到后续引擎
扎根≥2    打第二张扎根卡                   德鲁伊 +2/+2
封印≥1    打出任意古木强化（成长自动封印）    世界树之芽 +4/+4；林海共鸣 全体圣盾
封印生命≥64  强化约 2 次                   扎根爆发 恢复6
封印≥2    第二个单位被强化                  盛放 +6/+6
封印生命≥128 强化约 3 次                   永续 +4/+4 且 恢复8
封印生命≥256 强化约 4 次                   盖亚之赐 +8/+8

扎根 14 / 疯长 3 时：(6+14)×8 = +160；(8+14)×8 = +176；(4+14)×8 = +144
⇒ 盛放/盖亚之赐/永续各打一次即可跨过 512
```

**关键**：门槛**恰好就是达成 512 所需的铺垫步骤**，所以条件不是外加的税，
而是把"你走到哪一步了"写在卡面上。**这正是 owner 要的"高收益卡要有发动条件"。**
