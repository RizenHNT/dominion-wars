# Dominion Wars 卡牌设计可操作工作流

版本：1.0  
用途：将人类设计理念稳定地转换为卡牌方案、结构化字段、初始数值和可复验结论。  
性质：方法论与执行流程，不是新规则，不自动批准任何卡牌或平衡数值。

## 1. 目标

本工作流面向包括低参数模型在内的所有执行者。执行者不需要自行理解完整游戏，
只需严格按照输入、步骤、门禁和输出格式工作。

工作流解决四个问题：

1. 保留人类所有者的设计理念，不让数值调整改变卡牌幻想。
2. 防止模型把卡名、标签、规则文本和实际字段写成互相矛盾的内容。
3. 将“设计”“实施”“验证”分离，避免一个模型同时发明规则并宣布通过。
4. 让每次改动都可以小批次复核、撤回和继续接力。

## 2. 权威顺序

执行前必须按以下顺序读取来源。发生冲突时，高位来源优先。

1. 人类所有者在当前任务中的明确决定。
2. `docs/RULES.md` 中已启用、已冻结的规则。
3. `docs/effects.contract.md` 与当前 Runtime Contract。
4. `data/schema/cards.schema.json`。
5. C# Engine 当前能够执行的字段和动作。
6. 已批准的卡牌规格或阵营设计宪法。
7. 历史卡牌、Java 行为、旧设计包和生成器输出，仅作为参考。

如果两个高位来源冲突，输出 `HUMAN_REQUIRED`，不得自行选择一个版本。
候选机制、旧实现和模型常识不能覆盖人类决定。

## 3. 三层设计模型

每张卡必须拆成三层。修改低层不得改变高层。

### 3.1 设计灵魂层

由人类所有者批准，包含：

- 卡牌幻想；
- 玩家为什么想使用它；
- 它推动的阵营计划；
- 对手可以怎样应对；
- 使用失败时承担的风险；
- 不允许被修改的内容。

### 3.2 规则结构层

由策划或 PL 转换，包含：

- 卡牌类型；
- 触发时点；
- 来源区域；
- 目标集合；
- 效果动作；
- 结算后的区域；
- 持续时间；
- 反制窗口；
- 胜利条件贡献方式。

### 3.3 数值外壳层

由数值策划、模拟和测试反复调整，包含：

- 打印惩罚值 P；
- 惩罚降临费用 P'；
- 攻击与生命；
- 效果数值；
- 提交、上传、下载等动作费用；
- 阈值、次数、持续回合；
- 卡组数量配额。

数值外壳可以修改，设计灵魂不能因平衡调整被替换。

## 4. 角色隔离

即使同一个模型依次承担多个角色，也必须分轮执行，不能混合输出。

### 4.1 设计角色

允许：分析卡牌职责，提出保留、改写或暂缓建议，填写设计规格。  
禁止：修改 JSON、修改规则、宣布数值平衡。

### 4.2 实施角色

允许：严格按照已批准的改写表修改字段。  
禁止：增加改写表未声明的效果、目标、关键词或数值。

### 4.3 QA 角色

允许：读取规则、Schema、代码和改动，运行检查并分类问题。  
禁止：直接修生产卡牌、替设计者选择方案、把未验证内容写成 PASS。

## 5. 批次限制

- 每个批次最多处理 10 张卡。
- 每批只处理一个阵营、一个机制主题或一个问题类型。
- 四张统领必须各自作为独立批次审查。
- 不得一次重写 540 张卡。
- 单张卡出现歧义时，标记该卡 `HUMAN_REQUIRED`，继续其他独立卡牌。
- 未获批准时，不覆盖正式 `data/cards/`。

## 6. 阶段 A：建立阵营设计宪法

每个阵营必须先填写以下表格。缺任何一项时，不得开始批量设计。

```text
阵营：
一句话体验：
主要获胜体验：
主要游戏循环：
前期行为：
中期行为：
后期行为：
三个招牌机制：
两个明确弱点：
对手的三个反制出口：
该阵营失败时应有的表现：
禁止出现的行为：
不可修改的世界观或产品决定：
可由数值测试调整的部分：
```

### 6.1 当前四阵营的设计基线

本表只概括当前方向。若与更新后的 `RULES.md` 冲突，以规则书为准。

| 阵营 | 体验承诺 | 主要循环 | 主要失败条件 |
|---|---|---|---|
| 烈焰 | 主动进攻并压迫王城 | 铺场、攻击、突破防线、破城 | 场面被清、惩罚值资敌、统领暴露 |
| 机械 | 弱小低费机械经过区域转换产生价值 | 登场、提交、上传、栈顶下载 | 载体被清、队列或栈顺序不利、转换过慢 |
| 深海 | 通过无力与弃牌逐步取得控制 | 制造手牌压力、限制资源、达成弃牌进度 | 对手快速倾泻手牌、早期压力突破控制 |
| 古木 | 承担前期压力并培养巨型单位 | 累积扎根/疯长、强化、封印、成长 | 关键单位被连续处理、强化速度不足 |

## 7. 阶段 B：只选择首发可玩卡池

540 张生成内容先视为候选库。首轮只选择每阵营一套合法的 59 张主牌，
再配 1 张统领。补充池保持冻结，不删除。

### 7.1 默认类型骨架

第一版可使用以下起点；偏离时必须写出理由。

| 类型 | 默认数量 |
|---|---:|
| 随从 | 32 |
| 咒文 | 15 |
| 伏击 | 6 |
| 惩罚牌 | 6 |
| 合计 | 59 |

### 7.2 主职责骨架

每张牌只能有一个“主职责”，可以有少量次要标签。

| 主职责 | 默认卡位 |
|---|---:|
| 低风险启动牌 | 12 |
| 阵营机制启动器 | 10 |
| 机制收益牌 | 10 |
| 交互或解场 | 8 |
| 防守或恢复 | 6 |
| 惩罚响应 | 5 |
| 伏击 | 5 |
| 签名终结牌 | 3 |
| 合计 | 59 |

若卡牌同时满足多个职责，只能选择其中一个作为主职责，避免重复计数。

## 8. 阶段 C：逐卡意图审查

每张卡先填写意图卡，不得直接编辑 JSON。

```text
cardId：
卡名：
阵营：
候选状态：KEEP / REWRITE / HOLD / HUMAN_REQUIRED
卡牌幻想：
主职责：
推动的阵营机制：
玩家使用它的理由：
触发时点：
来源区域：
合法目标：
结算结果：
结算后区域：
对手反制：
失败风险：
不可修改项：
可调数值项：
依据：RULES 行/规格条目/人类决定
```

### 8.1 状态判定

- `KEEP`：幻想、职责、字段和规则一致，仅需数值微调。
- `REWRITE`：核心创意可保留，但效果、目标或时点需要重写。
- `HOLD`：重复、没有卡组职责、依赖未实现机制，暂不进入首发卡池。
- `HUMAN_REQUIRED`：多个方案会改变设计理念或规则，必须由人类决定。

## 9. 阶段 D：字段规范化

低端模型必须逐项填写，不允许从卡面自然语言直接猜 JSON。

### 9.1 效果六元组

每个效果必须规范化为：

```text
触发器 + 来源区域 + EffectAction + Target + Amount/Param + 结算后区域
```

示例：

```text
主动打出 + 手牌 + DAMAGE + ENEMY_MINION + amount=2 + 咒文入墓地
```

缺少任意一项时，不能进入实施阶段。

### 9.2 SELF 目标规则

- 随从在战场结算自身能力时，可以使用 `SELF`。
- 咒文、惩罚牌和伏击默认没有可被强化的随从身位，不得使用
  `BUFF:SELF` 或 `GRANT_KEYWORD:SELF`。
- 这类牌若要强化己方随从，应使用获批的己方随从目标。
- 伏击牌若要保护触发对象，必须明确该对象是谁，不能写模糊的 SELF。
- 王城互动必须使用明确支持王城的动作或目标语义，不能只加“破城”标签。

### 9.3 关键词规则

- 关键词表示持续或规则性行为；一次性动作使用 EffectAction。
- 关键词必须同时满足：规则书有语义、Schema 有枚举、引擎有行为、QA 有测试。
- 只被 Schema 接受、但引擎不执行的关键词不得进入首发卡池。
- 标签只用于分类和检索，不能代替实际效果。

### 9.4 时点与区域规则

| 语义 | 应写入的位置 |
|---|---|
| 打出时触发 | `onPlayEffects` |
| 被惩罚抽到后追加 | `punishEffects` |
| 伏击触发 | `ambushEffects` |
| 吟唱完成 | `chantEffects` |
| 机械提交瞬间 | `commitEffects` |
| 机械上传进入云端 | `pushEffects` |
| 机械下载离开栈顶 | `pullEffects` |

不能为了“让效果运行”而把提交、上传或下载塞进错误时点。

## 10. 阶段 E：阵营专项门禁

### 10.1 烈焰

- 标记为破城的牌必须实际提高破城能力。
- 合法手段包括攻击能力、突破嘲讽、攻击强化或明确王城互动。
- “破城”标签本身不计为机制实现。
- 大量治疗、慢速资源循环或无关控制效果必须标记 `REWRITE`。
- 快攻的强度必须伴随场面被清或资敌的失败风险。

### 10.2 机械

每张进入首发池的机械牌必须分别检查：

```text
出牌效果：
commitCost：
commitEffects：
uploadCost：
pushEffects：
downloadCost：
pullEffects：
是否需要下载载体：
进入提交队列的来源：
下载后的去向：
```

- 出牌不自动等于提交。
- PUSH 属于结束阶段自动处理，除非卡面明确声明例外。
- PULL 只能处理己方云端栈顶，并在结算后进入墓地。
- ROLLBACK 只选择提交队列中的合法卡，费用不返还。
- 费用字段没有实际支付来源时，不能进行强度结论。

### 10.3 深海

- 弃牌必须写明来源、数量、随机性和失败条件。
- 手牌为空时效果如何处理必须明确。
- 弃牌胜利不能只靠大量随机弃牌堆叠；必须保留对手主动应对空间。
- 无力、解场、防守和弃牌推进应共同构成控制体系。
- 未冻结的潮位机制只可进入 `HOLD`，不得伪装成已实现字段。

### 10.4 古木

- 强化目标必须是合法己方单位，或规则明确允许的共享王城。
- 普通强化、扎根增幅、疯长增幅和封印必须分开记录。
- 只有受批准增幅的强化才触发封印。
- 目标离场时已支付代价不返还。
- 胜利单位必须满足规则规定的归属、非统领和封印条件。
- 阈值属于数值外壳，应通过多个候选值测试，不得只凭公式定稿。

### 10.5 中立

- 提供通用工具，但效率应低于对应阵营专精牌。
- 不得成为全游戏唯一的基础防御、嘲讽或解场来源。
- 不得无代价补齐某个阵营被刻意保留的弱点。

## 11. 阶段 F：重复与名实检查

文本不同不等于卡牌不同。以下任一情况视为机械重复：

- 类型、费用、身材、关键词和全部效果相同；
- 只修改卡名或添加“老兵/精英”后缀；
- 只增加无运行时语义的标签；
- 数值变化没有改变任何使用决策；
- 同一家族的三个版本没有形成学习或构筑上的差异。

同一家族推荐使用以下三个不同职责：

1. 基础版：简单、稳定、介绍机制。
2. 进阶版：增加条件或协同。
3. 构筑版：强收益但有明确风险或限制。

卡名也必须通过幻想检查。例如“灼烧”默认不应产生治疗，除非卡面故事和规则
明确解释这种反转。

## 12. 阶段 G：数值初稿

数值模型只提供初值，不负责决定卡牌是否有趣。

### 12.1 调整数值的优先顺序

卡牌过强或过弱时，按以下顺序调整，尽量不改设计灵魂：

1. 调整 P、P' 或机械动作费用。
2. 调整数值量。
3. 收窄或扩大目标集合。
4. 增加或放宽条件。
5. 延后或提前触发时点。
6. 调整稳定性、随机性或卡差。
7. 只有前六项都不能解决时，才返回设计角色重写效果。

### 12.2 公式使用限制

- 随从身材公式不能直接用于无身材的咒文、伏击和惩罚牌。
- 不同卡型必须使用各自的预算线或同职责基准牌。
- 任何公式都不能给不可执行的效果计价。
- 未支付的费用不能作为平衡成本。
- 关键词没有运行时行为时，其预算价值为 0，并且卡牌不能通过门禁。
- 每次只改变一个主要变量，便于解释测试结果。

## 13. 阶段 H：五级验证

### H1 结构验证

- JSON 可解析；
- Schema 通过；
- ID 与名称符合规范；
- 字段、枚举、目标和动作存在；
- 没有未知字段或静默默认值。

### H2 语义验证

- 文本与结构化效果一致；
- 卡名与效果不冲突；
- 触发时点、目标和区域有效；
- 标签没有代替真实效果；
- 对手至少有一个明确反制出口。

### H3 单卡运行验证

- 正常结算；
- 无合法目标时按规则失败；
- 费用不足或条件不满足时无副作用；
- 区域转移正确；
- 事件和快照可观察；
- 不泄漏隐藏信息。

### H4 卡组闭环验证

对每套 59+1 检查：

- 起手是否有可执行动作；
- 核心机制能否启动；
- 收益牌是否有足够启动器；
- 胜利条件在合理对局内可达；
- 对手加入常见反制后仍有恢复路径；
- 卡组失败时是否符合阵营设计宪法。

### H5 对局与体验验证

至少记录：

- 先后手胜率；
- 四阵营交叉胜率；
- 对局回合数中位数；
- 胜利条件实际触发比例；
- 无法使用的死牌比例；
- 手牌溢出、长连锁和无响应对局比例；
- 对手看到威胁后拥有可操作回合的比例；
- 人类测试者是否能说出“我为何赢”和“我如何能阻止对方”。

40%–60% 胜率和 12–18 回合只能作为初始观察带，不是自动通过标准。

## 14. 每批标准输出

每个模型必须只输出以下五部分：

```text
批次：
输入版本/文件：
处理卡牌：

1. 逐卡状态
cardId | KEEP/REWRITE/HOLD/HUMAN_REQUIRED | 原因 | 依据

2. 改写规格
cardId | 设计灵魂 | 触发 | 区域 | 动作 | 目标 | 结果 | 反制 | 可调数值

3. 未决问题
只写会改变产品设计的问题；每题提供影响，不代替人类选择。

4. 验证证据
检查项 | 命令/方法 | 通过数/总数 | 失败 | 跳过

5. 下一安全批次
只推荐一个，不自动扩大范围。
```

不得使用“看起来没问题”“应该能跑”“大致平衡”作为证据。

## 16. 实施提示词模板

```text
你是【实施角色】。只根据已批准的逐卡改写规格修改数据。

禁止：
- 改规则；
- 改未列出的卡；
```

## 17. QA 提示词模板

```text
你是【QA 角色】。不得修改生产卡牌。

逐张验证：
1. 是否符合批准的设计灵魂；
2. 文本是否与字段一致；
3. 动作、目标、时点和区域是否合法；
4. 是否存在无运行时行为的关键词；
5. 是否能被当前引擎真实执行；
6. 是否有至少一个对手反制出口；
7. 数值测试是否只调整了获批的外壳变量。

结论只能是 PASS / FAIL / BLOCKED / HUMAN_REQUIRED。
没有运行证据时不得写 PASS。
```

## 18. 应用于当前 v13 候选库的顺序

1. 冻结现有 540 张候选库，不直接覆盖正式数据。
2. 先单独审查四张统领。
3. 每阵营从 main 候选中选 59 张，形成四套首发预组。
4. 修复无效 SELF 目标、无效 P'、伏击惩罚降临和错误时点。
5. 将机械牌迁移到 commit/push/pull 专用字段。
6. 移除或暂缓没有完整运行时行为的关键词牌。
7. 清理机械重复与名实冲突，不以文字后缀伪装差异。
8. 为随从、咒文、伏击和惩罚牌分别建立初始预算基准。
9. 完成单卡运行验证后，才接入临时测试数据。
10. 跑四阵营卡组闭环、交叉对局和人类体验测试。
11. 人类所有者确认体验后，才迁移到正式 `data/cards/`。

## 19. 完成定义

一张卡只有同时满足以下条件才是 `DONE`：

- 设计灵魂经批准；
- 在59张预组中有明确职责；
- 文本与字段完全一致；
- 动作、目标、时点和区域均已实现；
- 单卡测试通过；
- 卡组中可以合法使用；
- 存在明确反制或失败条件；
- 数值经过至少一轮对局验证；
- QA 有可复验的通过证据。

仅有 Schema 通过、公式在区间、文字唯一或模型自评通过，均不等于卡牌完成。
