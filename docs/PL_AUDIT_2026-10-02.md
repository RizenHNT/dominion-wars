## 8. 代码级审核（逐行读实现后发现的缺陷）

> 本节回应 owner 的追问：「你查看了具体代码么？具体实现上你有挑错么」。
> **§7 是内容层，本节是逐行读代码后的实现缺陷。** 每条都附可复现证据。

### 8.1 【中高】`data/balance.json` 有 15 个键，C# 只认 5 个 —— 改另外 10 个在实机静默无效

**证据**
- C# 的键映射 `src/Data/BalanceTable.cs` `RuleKeyByField` **只有 5 项**：`handLimit`、`pioneerHandLimitBonus`、`pioneerOpponentPunishBonus`、`pioneerSelfPunishDiscount`、`maxPunishResponsesPerRound`。
- Java 的 `src/main/java/com/dominionwars/data/Balance.java:apply()` 读 **15 项**（含 `royalCastleEnabled`/`royalCastleMaxHp`/`royalCastleBreakVictoryCount`/`reshuffleLoseAt`/`reshuffleIncludesHand`/`chainLimit`/`deckMin`/`deckMax`/`openingHand`/`drawPerTurn`/`secondPlayerBonusDraw`）。
- C# 全库对 `royalCastleMaxHp`、`royalCastleEnabled`、`reshuffleLoseAt`、`chainLimit` **零引用**。取而代之的是硬编码：`MatchSetup.cs:47 OpeningHandSize = 5`、`MatchSetup.cs:67 CastleHealth = 75`、`PlayCardActionHandler.cs:15 DefaultChainLimit = 20`；Unity 用的是自己的参数 `CastleEnabled`/`CastleHealth`（`RuntimeBootstrap.cs:219-221`）。

**后果（可复现）**：把 `data/balance.json` 的 `royalCastleMaxHp` 从 `75` 改成 `100` —— **Java 引擎会变，Unity 实机（C#）完全不变**。`docs/RULES.md` 开头承诺「所有数值默认值均可在 `data/balance.json` 中调整」，**C# 侧对其中 10 个键不兑现**。

**公平说明**：loader 并没有隐瞒——它把未识别的键写进 `notes`/`warnings`（`BalanceTable.cs:283-300`）。所以这不是欺骗，而是**「F24 已闭」这个说法把覆盖面说大了**：真正接上的只有 5/15。
**建议**：把「F24 已闭」改为「**F24 部分闭合（5/15 键）**」，并把剩余 10 个键单列为后续工作。

### 8.2 【中】T1 在 Java 引擎里**完全不存在** ⇒ 所有 Java 平衡实测都不是在出厂规则下跑的

**证据**
- 全 `src/main/java` 搜 `maxPunishResponsesPerRound` → **0 命中**；`Balance.apply()` 与 `toMap()` 都没有这个键。
- C# 侧则完整实现并在实机生效（`RuntimeBootstrap.cs:230 Rules = BalanceTable.LoadRules()`；`data/balance.json` 为 `1`）。

**后果**：owner 9/11 决定「一轮限 1 张反制」，但这个规则**只有 C# 有**。而**古木 71.7% 胜率、480 局选卡组、威胁估计器校准这些平衡结论都是用 Java 跑的**（`PL_FINAL_DECK_2026-09-24.md` 自述「Java 引擎，60 局/卡组」）。
⇒ **这些平衡数字是在「反制不设上限」的规则下测出来的，与出厂游戏不是同一套规则。** 这会让平衡结论系统性失真，且失真方向恰好指向 T1 想解决的问题（反制链过强）。

**建议**：这属于**规则实现分叉**，优先级应高于新卡设计。在 Java 实现 T1 之前，不应再用 Java 实测数字作为平衡决策依据——否则等于用另一套规则验证这套规则。

### 8.3 【中】读盘失败时的诊断消息**不实**

**证据**：`src/Data/BalanceTable.cs` 两处在回退时打印
「使用内置默认值（**与 data/balance.json 一致**）」——`:131`（路径非法）、`:195`（找不到文件）。
而 `BalanceTableTests.cs:161-163` **断言**这条字符串必须出现。

**事实**：回退值对 4 个字段确实与磁盘一致，但 `maxPunishResponsesPerRound` **不一致**（回退 `0`，磁盘 `1`）。
同一文件里 corrupt 分支的措辞才是正确的：「**无法确认**与磁盘数据一致，可能改变本局规则」。

**后果**：文件缺失时，Unity 会**静默把 T1 关掉**，同时打印一句「与磁盘一致」。**这与 Java 侧刚被修好的缺陷完全同构**（`Balance.java` 注释原文：「内置默认值必须与 data/balance.json 一致——否则读盘失败时会静默换一套规则」）——**Java 修了，C# 没修。**
**建议**：把该消息改为与 corrupt 分支一致的「无法确认与磁盘数据一致」，或把 C# 内置默认值对齐到 `1`（需 owner 定：回退时 T1 应开还是关）。

### 8.4 【低】两处生产代码注释与出厂数据互相矛盾

- `src/Engine/Rules/MatchRules.cs:76`：「对应 `data/balance.json` 的 `maxPunishResponsesPerRound`（**出厂 0**）」
- `src/Engine/Turns/PlayCardActionHandler.cs:347`：「（`data/balance.json: maxPunishResponsesPerRound`，**出厂 0 = 关闭**）」

而 `data/balance.json` 实际是 **1**。注释写的是**回退值**，却标成「出厂值」，会误导后续维护者。
