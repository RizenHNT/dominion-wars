## 3. 落地方式

```powershell
# 1) 先看会改什么（不写盘）
pwsh -NoProfile -File build-output\pl-flip\apply-flip.ps1 -T1 -M1

# 2) 确认后落盘（自动备份 + 落盘后自校验）
pwsh -NoProfile -File build-output\pl-flip\apply-flip.ps1 -T1 -M1 -Apply

# 3) 回退
pwsh -NoProfile -File build-output\pl-flip\apply-flip.ps1 -Revert
```

脚本设计要点：
- **默认 dry-run**；`-Apply` 才写盘。
- **逐行文本替换**而非 JSON 反序列化再序列化 —— 后者会把整份文件重新排版，产生成百上千行无意义 diff；现在只动 7 行。
- 替换前**先校验每处查找串的出现次数**（不符就中止并报错），避免"文件已被改过却盲目替换"。
- 落盘前备份到 `build-output\pl-flip\backup-<时间戳>\`，落盘后自校验新值出现次数与旧值归零。
- **已实测**：dry-run 完整打印 7 处改动、且 `git diff -- data` 只有既有的那 1 行（脚本确实没写盘）。

### 3.1 脚本自身的红→绿：沙箱自测抓出 2 个真 bug

我把整份脚本连同 `data\balance.json` + `data\cards\machine.json` 的**副本**放进沙箱目录（`build-output\pl-flip\selftest\`，镜像仓库布局）跑真实的 `-Apply` / `-Revert`，**没有直接对仓库下手**。初版当场失败：

| bug | 症状 | 后果（若直接落盘） |
|---|---|---|
| **① 同文件多处改动互相覆盖** | 每个 edit 各自基于**原始**文本写盘，后写的覆盖先写的 | `machine.json` 的 4 处只落 1 处；自校验报 3 个 FAIL。**dry-run 看起来完全正常，因为 dry-run 不写盘** |
| **② `-Revert` 相对路径算错** | `Substring` 长度算错，拼出 `...\selftest\+\2026...\data\balance.json` | 回退功能不可用（报 "Could not find a part of the path"） |

**修正后实测全绿**（沙箱内，仓库零写入）：

```
APPLY  : backed up ×2 → wrote ×2 → 自校验 5 项全 OK
         maxPunishResponsesPerRound = 1
         leader winParam=5  alpha winParam=5
         提及「6次下载」= 0 处；提及「5次下载」= 4 处
REVERT : 从备份恢复 2 个文件
         maxPunishResponsesPerRound = 0
         leader winParam=6 ；提及「6次下载」= 4 处（完全还原）
真实仓库: git diff -- data 仍只有既有的那 1 行 ⇒ 沙箱测试未污染仓库
```

**教训（值得记档）**：dry-run 通过**不能**证明 `-Apply` 正确 —— 恰恰是这个脚本的初版在 dry-run 下完美、在落盘时会把 M-1 打成半成品。凡"会改数据的工具"，必须**在副本上真跑一次 apply 并真跑一次 revert**。
