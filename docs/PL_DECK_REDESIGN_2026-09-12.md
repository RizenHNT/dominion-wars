## 1. 什么叫"策略性" —— 先定成可测的东西

"有策略性"很容易变成一句空话，所以先把它拆成**可以量出来的五条**。后面的卡表要能对上这五条，
测试要能给出数字，否则就是自说自话。

| # | 判据 | 怎么测（可执行） |
|---|---|---|
| **S1** | **代价与收益存在张力**：强牌必须为强度付代价，弱牌有可用之处 | 改单卡强度后，AI 的**选中率与胜率**都要动；若只有胜率动而选中率不动，说明代价没被感知 |
| **S2** | **存在真正的选择**：不是"每回合把能打的都打出去" | 统计**平均每回合出牌数**与**结束回合时机**分布；非退化时不应恒等于"打完为止" |
| **S3** | **有反制空间**：对手有手段应对主胜利轴 | 注入"面向某轴的**反制牌**"，看该轴的胜率是否下降、AI 是否改打别的轴 |
| **S4** | **不存在退化打法**：没有单一必胜套路 | 用不同 playstyle（6 套出厂打法）× 多次采样，看**最优打法是否唯一且恒定** |
| **S5** | **不同阵营赢法不同**：不是"谁身材大谁赢" | 各阵营的**胜利原因分布**应显著不同（`win.*` 事件分布） |

**这五条里 S2/S4/S5 现在就能测**（引擎已有事件日志与多 playstyle 框架）。
**S1 需要先修权重**（见 §5），否则 AI 看不见代价，测 S1 是白测。

## 2. 深海：侵蚀印记（本提案的核心，待批）

### 2.1 机制

**侵蚀（Erosion）**：一个**公开挂在玩家身上的可累积状态**。
- 由深海卡的效果**施加给对手**（"侵蚀 N"）。
- **不是一个新的胜利条件**，而是一个**中转资源**：侵蚀累积到一定程度会被**转成弃牌**，
  而弃牌才是深海已有的胜利轴（`OPPONENT_DISCARD_COUNT / 18`）。

**一句话**：`深海出牌 → 对手被侵蚀 → 侵蚀转弃牌 → 弃牌数达 18 获胜`。
侵蚀是**中间那一层**，它的意义在于：

- 让"干扰"**看得见**（对手能知道自己被侵蚀了多少，因而能应对）；
- 制造**两步节奏**（先积累、后引爆），而不是"出一张牌就弃一张"的一步到位；
- 给双方**决策点**：深海方要选"现在引爆还是再攒"，对手要选"花资源清侵蚀还是忍着"。

### 2.2 三个必须定死的细节

| # | 问题 | 提案 | 理由 |
|---|---|---|---|
| **D1** | 侵蚀**怎么转**弃牌 | **由卡牌主动消耗**（"消耗对手身上全部侵蚀，每点弃 1 张"）＋ **一个自动阈值**（到 5 层时结束阶段自动转 2 张） | 纯卡牌消耗 → 深海方攒着不引爆就能无限拖；纯自动 → 没有决策。两者都给，但**自动阈值设高**，让"卡牌引爆"是主要玩法 |
| **D2** | 侵蚀**上限** | **8** | 必须有上限，否则"攒到 20 再爆"成为唯一解，违反 S4 |
| **D3** | 对手**能不能清** | **能**，但只有明确的卡牌效果能清（不自动衰减） | 不清除 = 无解（违反 S3）；自动衰减 = 深海白做功（违反 S1）。**只有卡牌能清**，把反制变成一种资源选择 |

### 2.3 待 owner 拍的两点

1. **侵蚀与"潮位"是同一个东西还是两个？** 提案：**合并为一个**（名字用「侵蚀」）。
   两个并行状态会让深海同时有两条中转轴，玩家和 AI 都要同时跟踪两套数，**测试也更难判断是哪条在起作用**。
2. **侵蚀要不要进快照**（AI 能否看见）？
   提案：**必须进**。否则 AI 看不见侵蚀 → 又是一次"仪器没有这个输入"（本项目已犯过：
   费用、生命、打脸都是同一个病）。**这条没有商量余地，我会按"必须可见"实现。**

## 3. 古木：机制已齐全，只需补卡

`RULES.md §12.2` 现有机制与 owner 意图**已经完全吻合**，不需要新机制：

| owner 意图 | 仓库已实现 |
|---|---|
| 养怪给 buff | **扎根**（每层 +1/+1，累计不消耗）＋ **疯长**（每层 ×2，上限 3） |
| 攻击欲望低 | **受增幅单位进入「封印」：不能攻击，但可继续被强化** |
| 后期 / 解场多 / 怪少 | 封印单位不攻击 ⇒ 前期只能靠解场拖时间；胜利阈值 **512** 天然是后期 |
| 后期爆发 | 扎根+疯长叠乘后一次性把某个封印单位推过 512 |

**所以古木的"设计"其实是**：控制**扎根/疯长卡的密度**、**解场牌的密度**、以及**允许出现的随从数量上限**，
让"怪少、解场多、攻击欲望低"在**卡组构成**上成立，而不是靠规则强制。

**这一套是三个阵营里最容易测的**（轴单一、阈值明确），建议**第二个做**。

## 4. 机械：机制已齐全，但有一处需要确认

`RULES.md §12.4` 现有流程与 owner 意图吻合：

```
出牌惩罚 0（= "1 费"）→ 上场当普通随从 → 手动提交(COMMIT) → 结束阶段自动上传(PUSH)进云端栈
→ 用场上下载载体下载云端栈顶(PULL) → 累计下载 6 次获胜
```

| owner 意图 | 仓库已实现 |
|---|---|
| 怪兽全 1 费 1/1 | 出牌惩罚 **0** ＋ 基础身材偏低（**"1 费"在本游戏就是出牌惩罚 0**） |
| 前期上传、上传/提交时收益 | `uploadEffects` / `commitEffects` 均已实现并在对应时点结算 |
| 后期统领+下载爆发 | `machine_leader` 地标第 2 层召唤 `machine_alpha`，之后继续下载达成 `PULL_TOTAL_GE 6` |
| **回滚控制云端栈顶** | **下载只能取栈顶**（不能跳过）＋ **回滚**把提交队列的卡移回手牌 ⇒ 需要回滚来**重排栈** |

**"1 费 1/1"需要 owner 确认一处**：本游戏**没有法力费**，"费用"就是**惩罚值**。
出牌惩罚 0 意味着**打机械卡不需要给对手抽牌**，代价全在 `COMMIT/PUSH/PULL` 时付。
若你说的是"出牌惩罚 0、身材 1/1"，**现状已经是这样**，无需改规则；
若你想要**出牌也要付代价**，那要改数值——**这条请你确认**。

## 5. 必须先修的两条 AI 权重 —— **已撤销，因为实测推翻了它们**

| 特征 | 现状 | 我先前提议 | **实测结果** |
|---|---|---|---|
| `face` | **0** | 改成 400（让打脸能压过出牌） | ❌ **提议作废** |
| `punish` | **0** | 改成 −2 | ⏸ **owner 裁定"就这样就行"，不改** |

**`face` 的提议被实测推翻**，据如下（`AiWeightCounterfactualTests`，912 个 ACTION 决策、同一批局面）：

```
face=0    → 打脸已广告 142 次，采用 0 次
face=300  → 打脸已广告 142 次，采用 0 次      ← 提高 300 分，一次没动
face=400  → 打脸已广告 142 次，采用 0 次      ← 已超过出牌的 500，还是没动
```

**权重根本不是瓶颈。** 我说"改 face 就能让打脸被选中"是错的，证据是它差着 300 分都不动。
所以**撤回该建议，不再提**。至于 400 为什么仍然不选，那是一个独立问题（可能 `WinAxis=700`
或其它特征在攻击上另有取值），**但不必为卡组设计解决它** —— 新手卡组不该围着打脸转。

**附带查明的一件硬约束**：`PlaystyleTests.DefaultWeightsOrderAdvertisedActionsExactlyLikeTheRetiredRank`
在 600+ 局面、三重比较下断言"默认权重**逐位复现已退役的手写排序**"，而那个排序里**出牌排在打脸之前**。
所以**任何把 `face` 提到 `board` 之上的改动都会打破一个当前为绿的既有不变量** ——
这条不变量是"权重表能复现历史测量所用策略"的迁移证明，**不该为了让新改动能过而被改写**。
这正是我把这件事先测后改、而不是直接改权重的原因。

**权重最终结论：不动。**（owner 裁定 + 上述实测一致。）

## 5.1 白板曲线：**已测，并得出否定结论**

在修正引擎上跑了单卡数值消融（攻击 +1/+2/+3、生命 +1/+2/+3、惩罚 +1/+2），
同一批局面、两个座位合并、其余卡全不动（`AiStatCurveTests`）：

| 焦点卡 | baseline | +3 攻击 | +3 生命 | +2 惩罚 |
|---|---|---|---|---|
| `sea_kraken` vs `flame_deck` | **100%** | 100% | 100% | 100% |
| `wood_bear` vs `flame_deck` | **40%** | 40% | 37.5% | 40% |

**这张"曲线"是平的，所以它还不是一条曲线。** 两条结论：

1. **胜率由"哪套卡组"决定，不由单卡数值决定。** 海对火 **10/10 全胜**，古木对火 40% ——
   匹配关系的影响远大于单卡 +3 身材。**在那之前，胜率不能当数值标尺。**
2. **所以现有卡组本身是不平衡的**，这不是仪器问题，是**设计输入的问题**。

**这对卡组设计是直接可用的结论**：新卡组的数值**不能靠"看胜率"来定**。
可用的标尺必须是**与结算无关的量**，例如：
- **选中率**（这张牌被选中的频率），
- **胜利轴推进速度**（`OPPONENT_DISCARD_COUNT` / `PULL_COUNT` / 封印单位生命 的每回合进度），
- **决策多样性**（每回合出牌数分布、结束回合时机）。

**下一步就是把标尺换成这些**，而不是继续加大胜率样本。

## 5.2 顺带修掉一个阻塞性缺陷：V3 自弃牌提交

白板曲线**第一次跑不出来，是因为大部分对局根本打不完**：

```
123/180 局完成    ← 修复前
 55x  all_rejected phase=ACTION chosen=PLAY_CARD reason=action.discard_selection_required
```

**55/180 局卡在"自弃牌提交不了"。** 这就是先前记录的 V3 缺陷，而它的代价比原先估计的大：
**它使任何整局测量（胜率、回合数、胜利原因分布）都不可用**。

**修法（按 owner 的弃牌裁定：窗口内玩家自选，超时系统丢）**，三层：

| 层 | 改动 |
|---|---|
| 边界 | 唯一一条受控例外：**自弃牌类 `PLAY_CARD` 允许额外携带 `selectedEntityIds`**，并**单独校验**它（数量 == 广告的 `discardRequired`；每个 id ∈ 广告的 `discardCandidateIds`）。其余字段仍**严格逐字匹配**，其它动作类型**完全不受影响** —— 没有放松整体校验 |
| 网关 | 自弃牌 `PLAY_CARD` 也允许从 `selectedEntityIds` 读取选择（原先只有 DISCARD 阶段允许） |
| AI | 策略**自己作出选择**并提交（引擎广告顺序的前 N 个候选），**不是网关静默代选** —— 选择发生在做决策的地方，然后交给边界校验 |

**结果**：

```
178/180 局完成    ← 修复后（剩 2 局是步数预算，不是死锁）
自弃牌提交 17 次，全部被引擎接受
  machine vs sea: required=2 selected=2 candidates=48 allChosenAreCandidates=True accepted=True
  sea vs wood:    required=4 selected=4 candidates=7  allChosenAreCandidates=True accepted=True
```

**C# 门禁 880/880、断言 140949。** 两个原先"记录缺陷存在"的测试已改为**正面契约**
（提交必须被接受、选择必须合法），因为让一个"这东西永远不行"的排除断言活过修复，
正是本项目反复出现的失败模式。
