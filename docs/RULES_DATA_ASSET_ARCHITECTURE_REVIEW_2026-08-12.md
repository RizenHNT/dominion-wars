# 规则、卡牌数据、素材与架构初审

> 状态：初审报告 / 讨论稿。结论用于决定下一阶段试玩切片，不代表已经批准的新规则。
> 原则：Java 是可运行的旧原型和行为参考，不是所有设计的最终答案。

## 1. 先说结论

目前的基础并不需要推倒重来：惩罚值、伏击、统领自动登场和事件链组合起来，有一个比较鲜明的游戏特色。

但现在还不能直接把 Java 原型搬进 Unity。主要原因不是“代码不能跑”，而是：

1. 新玩家要同时理解太多胜利方式和隐藏条件。
2. 卡牌字段里有几处“看起来是描述，实际上会改变规则”的混用。
3. 卡图目录有两套，实际读取路径不统一。
4. 结构化效果和手写 `text` 可能互相不一致。
5. 现有 AI 能完成对局，但还不是会算长期策略的“子代理玩家”。

## 2. 当前事实盘点

- 当前卡牌数据：91 张；4 个阵营卡组各 60 张普通卡 + 1 张统领，卡组文件各包含 20 种卡、每种 3 张。
- 卡牌类型：41 随从、37 咒文、9 伏击、4 惩罚牌。
- 所有 91 张卡都有 `text` 字段；其中 20 张是空文本，主要是没有特殊效果的基础身材卡/token 卡。
- 当前静态数据检查发现没有重复卡名；但存在若干“数值和效果完全相同、只换了阵营/名称”的卡对，例如普通伏击伤害、反制伏击、抽 1/抽 2、圣盾法术等。
- 当前类型字段快速检查通过：91 张卡没有发现伏击字段跑到非伏击卡、统领字段不完整、随从缺攻防、或有结构化出场效果却没有显示文字的情况。这个检查只能证明当前数据没有明显越界，不能证明文字和效果的全部语义相同。
- Java AI 对 AI 模拟平均约 20 回合；最近一次 1200 局汇总胜率：烈焰 61.0%、深海 54.3%、机械 45.0%、古木 39.7%。这只是早期警报，不是最终平衡结论，但说明四套牌目前可能不在同一强度区间。

## 3. 规则：哪些地方有趣，哪些地方会劝退

### 值得保留的核心

- **打牌会给对手抽牌**：每张牌的强度和“喂给对手多少资源”形成取舍，这是项目最有辨识度的地方。
- **惩罚连锁**：对手抽到可响应的牌时，可能反过来发动，能制造意外和反击。
- **伏击阶段**：玩家在行动前要猜对方下一步，能产生心理博弈。
- **统领自动登场**：统领什么时候被抽到，会改变局面，适合做故事感和阵营特色。

### 第一阶段试玩最需要收窄的地方

现在一局里同时存在：击败统领、王城、牌库循环、弃牌累计、连续不受伤、单回合惩罚抽牌、命运之门等多种终局方式。老玩家可以研究，新朋友第一次玩很容易只剩一句：“我现在到底该打谁？”

第一阶段不应该删除“每个统领拥有不同胜利方式”这个核心。更合适的做法是：试玩只选两套牌，但保留这两位统领各自不同的胜利目标，并在界面上固定显示：目标说明、当前进度、还差多少、对手能否阻止。

可以暂时不把所有 91 张卡和所有公共系统一次性放进试玩，但不能把统领胜利方式改成同一种。这样既保留牌组构筑意义，也避免新玩家第一次面对全部规则。

### 需要明确而不是继续猜的规则

1. `tags` 当前不只是分类。Java 的 `tagsFree` 会把相同 tag 变成“本回合同类只能用一次”。例如两张“增强”或两张“风暴”可能互相锁住。若这是设计意图，字段最好叫 `oncePerTurnGroup`；若只是卡牌标签，则应取消它的规则作用。
2. 统领自动登场、王城公共血条和双方统领门限叠加后，部分攻击目标可能不符合普通卡牌游戏直觉。试玩版必须在 UI 里明确写出“现在能否攻击统领/王城，以及为什么”。
3. 先驱威压会改变惩罚成本，但它和手牌上限、王城、特殊胜利同时存在，容易让先登场统领的一方获得过多优势。应先单独测试，而不是默认全部开启。
4. 20 层惩罚连锁是安全上限，不应被玩家当成普通玩法目标；第一阶段可以把连锁提示做清楚，必要时把实际体验上限调低。

## 4. 卡牌字段：现在清楚的地方与重复的地方

### 结构总体是对的

卡牌已经把“基础数值”和“触发效果”分开了：`attack/health`、`onPlayEffects`、`ambushEffects`、`punishEffects`、`chantEffects` 等，方向正确，适合以后接 Unity。

### 需要整理的重复/混用

- `text` 是手写显示文字，而效果已经在结构化字段里写了一遍。两者可能漂移；以后应以结构化字段为准，`text` 只作为人工覆盖或由工具生成。
- `tags`、`keywords`、`guard`、`kingSlayer`、`leader` 分属不同层，但玩家看到时都像“卡牌标签”。特别是 `tags` 目前会改变出牌规则，不能再把它当纯装饰分类。
- `leader: true`、`tags: [统领]`、`leaderDef` 三处都在表达“这是统领”。建议保留一个权威字段，其他只用于显示或由校验器自动推导。
- `type: PUNISH` 和 `punishActivatable` 不是完全重复：前者表示不能主动打出，后者表示普通卡也能有惩罚能力；但 UI 必须把这两个概念说清楚。
- `faction` 和 JSON 文件名都表达阵营。文件名用于组织可以保留，但应加一致性检查，避免卡被放错文件后出现两个阵营来源。
- schema 允许很多“与类型不相干”的组合，例如普通随从带 `ambushEffects`、非统领带 `leaderDef`。当前 91 张卡没有明显越界，但以后编辑器很容易造出无效卡。
- schema 里出现了 `summonedThisTurn` 这种运行时状态字段；它不应属于卡牌静态定义，应移到实例状态或快照结构。
- Java 的 `EffectSpec.extra` 会保留未知字段，而 schema 对效果对象是 `additionalProperties: false`。一个是宽松接受，一个是严格拒绝，边界需要统一。

## 5. 素材：透明组件和实际卡图要分开看

### 已经具备的

`design/runtime-kit-v1.30` 是可组合的 UI/卡面素材包：

- 清单共 320 项；
- 313 项标记为带透明/可组合资源；
- 实际 PNG 中 209 张有 alpha 通道；
- 有卡牌边框、卡背、印章、按钮、阶段图标、状态图标、纸张纹理和 SVG 源文件。

这部分适合直接搭第一阶段界面。

### 目前的实际卡牌图片

`data/art/` 目前有 4 张：`flame_leader`、`machine_alpha`、`sea_leader`、`wood_leader`。它们是 360×150 的普通不透明 RGB 横图，不是透明背景组件。

`data/cardart/` 目前只有说明文件，没有实际卡图。

更重要的是，Java 代码里同时存在两套读取路径：

- `CardPanel` / Web 服务的一部分读取 `data/art/`；
- `CardArt` 和编辑器主要读取 `data/cardart/`。

这会产生“素材明明放了，但某个界面不显示”的风险。试玩前应统一成一个目录和一个 `AssetAdapter` 入口。

### 合法性边界

文件清单和 SHA-256 只能证明资源没有被意外改坏，不能证明有版权或授权。当前仓库没有看到完整的来源/许可证记录，因此“文件可用”不等于“可以公开发布”。

## 6. 如果让现有子代理玩家来打

现有 Java `AiAgent` 的行为很适合做冒烟测试，但它的思路比较简单：

- 伏击阶段优先选“封场 > 专注 > 普通”；
- 行动阶段每回合大约只花一份惩罚预算，最多主动打 3 张有惩罚的牌；
- 对方牌库不够支付惩罚时不出牌；
- 目标优先选能击杀的高威胁随从，再考虑统领/王城；
- 弃牌时优先扔未激活惩罚牌、高费用或低身材牌。

它目前不会真正读懂“几回合后才有价值”的组合，也不会充分计算对方手里可能有什么伏击。

具体到卡组，大致会这样：

- **烈焰**：偏向直接伤害和群体伤害，看到合适时抢王城；容易打得主动，因此当前模拟胜率最高。
- **机械**：会使用抽牌、修复、护盾和直接伤害，但对“吟唱两回合后召唤/爆发”的长期价值估计不足。
- **深海**：会使用弃牌和抽牌，能盖专注伏击，但不会真正预测对方下一次抽牌来安排吞噬时机。
- **古木**：会盖封场、堆嘲讽和治疗，理论目标是维持连续不受伤；但 AI 主要在对方接近胜利时才反应，长期防守策略仍比较粗。

所以如果以后做 Unity 子代理，建议把 AI 分成两层：规则层负责“能不能做”，策略层负责“为什么现在做”。不要把当前 `playPriority` 直接当最终 AI。

## 7. 建议的下一步顺序

### P0：先定试玩规则，不加新卡

1. 选烈焰 vs 机械或烈焰 vs 古木作为首个对局，并保留两位统领各自的胜利方式。
2. 每套先用 8–12 种卡，而不是完整 20 种。
3. 王城、牌库循环等公共系统是否同时开启，作为试玩范围选项单独确认，不改变统领差异。
4. 保留 `tags` 的玩法意义，但在 UI 中用绿色提示“本回合可用”、红色提示“同类词条已使用/当前不可用”，并在卡牌详情解释原因。
5. 确认统领、惩罚连锁、伏击三条规则的玩家提示。

### P1：做数据质量闸门

- 按卡牌类型检查允许字段组合；
- 检查 `leader` / `leaderDef` / 统领 tag 一致；
- 检查 `text` 与结构化效果是否冲突；
- 检查阵营文件名与 `faction` 一致；
- 统一 `data/art` 与 `data/cardart`；
- 把素材来源、许可证、是否透明、尺寸和用途写入资产清单。

### P2：再接 Unity 试玩

- 先接卡面和两套卡组；
- 再接手牌、场面、伏击区、统领区、回合按钮和事件提示；
- 最后接完整终局和更多卡牌。

## 8. 本轮暂不自动改动的内容

- 没有修改规则数值、卡牌平衡或 Java 原型。
- 没有删除重复卡，也没有擅自合并字段。
- 没有把 B+ 控制结构写入生产 schema。
- 没有把素材宣称为已获得版权授权。

本轮已做一个不改变玩法的技术兼容修复：统一新卡图入口为 `data/art/`，同时保留 `data/cardart/` 旧目录回退，避免已有素材失效。

这些项目需要你或 MiniMax/PL 确认方向后，再进入实现任务。
