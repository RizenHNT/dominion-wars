## 1. 为什么必须做这件事（我们自己的实测就是最强论据）

**单个 AI = 一个点；卡牌调整需要的是区间。** 这不是理论担忧，本仓库已经量到两次：

| 证据 | 数字 | 出处 |
|---|---|---|
| 只改 AI 行为，机械阵营胜率 | **0.0% → 95.7%**（287/300，全部 `win.pull_total_ge`） | QA 预言机：让 AI 优先下载轴前后 |
| 只改 AI 行为，机械阵营胜率 | 34.17% → 50.00% | 本会话：`winParam`+`downloadCost` 双杠杆（引擎口径） |
| 同一引擎、只换策略的绝对胜率 | 深海 84.4 → 86.9 → 70.6（三种口径） | `PL_BALANCE_MEASUREMENT` §2/§3.2 |

⇒ **任何"某张卡超模/亏模"的结论，都可能是"那套 AI 不会用/太会用这张卡"。** 只有跑**多套不同打法**、看**区间与稳健性**，才敢据此改卡。这是本次卡牌调整数据通路的关键前置。

**另一个现实收益**：多打法矩阵能自动暴露"某张卡只有一种打法能用"这类设计问题（如果 5 套打法里只有 1 套能用某张卡，那张卡就是窄的）。

## 2. 业界做法与我们采纳/否决的理由

查到的几个方向：

- **加权评估函数 + 遗传算法进化权重**：[Evolving Evaluation Functions for Collectible Card Game AI](https://ar5iv.labs.arxiv.org/html/2105.01115)、[SCITEPRESS 版](https://www.scitepress.org/PublishedPapers/2022/108069/pdf/index.html) —— 用一组**特征权重**给动作/局面打分，再用 GA 进化权重。**这正是我们需要的形状**。
- **MCTS / AlphaZero 式 + 神经网络估值**（[CIG 2018 proceedings](https://project.dke.maastrichtuniversity.nl/games/files/proceedings-CIG2018.pdf)、[Unity/C# 自对弈 + MCTS 原型论文](https://tesi.univpm.it/retrieve/239eb88e-c904-4d12-9260-8a6f09b23d10/TESI%20DI%20LAUREA.pdf)）—— 强度导向。
- **自对弈强化学习**（如 [Dhumbal 卡牌 AI 对比研究](https://ar5iv.labs.arxiv.org/html/2510.11736)、[ByteRL 可被利用性](https://www.semanticscholar.org/reader/c804e9ca537647e5105d9fc2c5b4096cb4247bc4)）—— 训练一个强 agent，并研究它有多容易被针对。
- **商业卡牌游戏的工程实践**：分层决策（先分类动作，再在类内用启发式选点）、行为树、以及"按原型（archetype）分别调参"。

| 方向 | 采纳？ | 理由 |
|---|---|---|
| **加权特征评估 + 权重即打法** | ✅ **主结构** | 与文献一致；**一套代码 + 多组权重 = 多套打法**，成本最低；完全确定性；天然可解释（能回答"它为什么这么打"） |
| 按原型分档调参 | ✅ 采纳为落地形式 | 仓库里已有先例：`CHANGELOG_CASTLE §6.4`「烈焰仍需更好的破城 AI」——**按阵营定制 AI 是项目自己的历史诉求** |
| MCTS | ❌ 本期不做 | 我们要的是**多套可比较的打法**，不是**一个最强 AI**；MCTS 每次决策要模拟上千局，720 局×多打法的扫描成本不可接受；且它难以解释"为什么" |
| 神经网络估值 | ❌ 本期不做 | 无训练数据/算力预算；不可解释；且我们的瓶颈是**打法多样性**而非棋力 |
| 自对弈 RL | ❌ 本期不做 | 同上；而且会收敛到**单一**最优策略 —— 与"要多种打法"的目标相反 |

**一句话**：**本期目标是"覆盖面"，不是"棋力"。** 我们故意要几套**会犯不同错误**的 AI。

## 3. 架构（保持不变量）

### 3.1 必须守住的三条不变量（来自本会话已确立的约定）
1. **AI 只能从已广告的动作中选择**，返回的动作必须**逐字段来自广告**（含 payload），**不得**编造 `selectedEntityIds`/目标/卡片 id。
2. **AI 不得派生规则**：不读 `GameState`，只读**观看者安全快照** + 该快照的 `LegalActions`。
3. **确定性**：同输入同输出，无 RNG、无时钟。

### 3.2 形状：把现在的固定优先级泛化成"特征权重"

现在 `src\Adapters\Ai\AdvertisedActionPolicy.cs` 里 ACTION 阶段是一个**硬编码优先级**（有用的 PULL → PLAY_CARD → COMMIT → ATTACK → END_TURN）。把它改成：

```
score(action) = Σ  w_i × f_i(action, snapshot)
选 argmax(score)，并列时按稳定次序
```

- `f_i` = **特征**，只从"广告动作 + 观看者快照"计算，例如：
  - 该动作是否为生命周期动作（PULL/PUSH/COMMIT/ROLLBACK）
  - 是否会推进自家胜利轴（如机械的 `CloudStackCount`/`PullCount`、古木的载体血量）
  - 是否造成伤害 / 是否打脸 vs 换场
  - 是否消耗手牌 / 是否补充手牌
  - 该动作的**惩罚成本**（广告里的 `punish` 字段，属于广告数据，不是派生规则）
  - 是否结束回合
- `w` = **打法权重向量**。`IPlaystyle { string Id; IReadOnlyDictionary<string,int> Weights; }`
- **这就是全部差异**：打法 = 一组 `w`。新增打法 = 新增一组数字，**不新增决策代码**。

### 3.3 与既有代码的关系
- `AdvertisedActionPolicy` 的 `Rank`/`IsUsable`/`OrderAdvertisedActions` 保留为**默认打法**（现行为 = 一组特定权重），**行为不得改变**（防止把已测读数作废）。
- `AiTurnCoordinator` **不动**（它只管节奏）。
- Unity `RuntimeAiPolicy` 门面**不动**，只是它背后的默认打法不变。

**⚠️ 实现期更正（2026-09-11，实现者实证，我采纳）：本节原话"退休的硬编码优先级 = 一组权重"在字面上是 FALSE。**
任何**语义特征**上的权重向量都无法复现那个 rank —— 它把**"不可下载的 PULL"排在 COMMIT 之上**（两者都是 lifecycle），又把 **ROLLBACK（lifecycle 动词）排在 END_TURN 之下**。若强行用语义特征拟合，就会被迫写出一组自相矛盾的权重。
实现者的处理方式我认可：**新增 `spend_field`（COMMIT）与 `chain_reverse`（ROLLBACK）两个特征**，使默认向量能精确复现 rank；同时**保留 `Rank`/`AdvertisedActionPriority` 作为公开的冻结参照**（而不是删掉），并另写一条"684 组广告 × 3 种比较、与**冻结副本**比对、0 差异"的测试来钉死等价性。
⇒ **结论：默认行为不变（已证），但"它就是一组权重"这个说法只在"加上了两个为它定制的特征"之后才成立。** 这正是为什么等价性必须**被测试证明**、不能靠设计意图宣称。

### 3.4 落点
- 新增 `src\Adapters\Ai\` 下：`IPlaystyle.cs`、`ActionFeatures.cs`、`WeightedPlaystyle.cs`、`PlaystyleRegistry.cs`。
- 特征计算必须**纯函数**且**可单测**（给定广告动作+快照 → 特征向量），这样"打法差异"可以被断言，而不是靠跑对局间接猜。

### 我的裁定与设计修正：**打法必须同时携带"响应立场"**

与其单独修 F32，不如让它归入本次打法框架 —— **响应立场本来就是打法的一部分**：

```
IPlaystyle = { Id, Weights（行动阶段打分）, ResponseStance（是否发动降临响应：Never / FirstInRound / Always） }
```

- `control` / `economy` ⇒ `Never`（怕喂牌，保守）
- `aggro` / `tempo` ⇒ `FirstInRound`（愿意用一次反打换节奏）
- `combo` ⇒ 视轴而定（机械更关心推进下载轴）
- **括号**：`bracket-decline` = `Never`、`bracket-accept` = `Always`、`bracket-first` = 现行生产默认（也是 `Never`）

**接线点**：`MatchFactory.cs:64` 把 `TurnActionRouter.CreateDefault(flow)` 改为传入由所选打法决定的 `IPunishResponsePolicy`。**这一步之后，打法才真正影响发行版，T1 也才真正开始起作用。**

### 3.5.1 分层澄清（实现期发现，值得写死）：`FirstInRound` 与 `Accept` 在 cap=1 下**等价**

`IPunishResponsePolicy.Decide(state, card, effectivePunish, chainDepth)` 是**无状态**的，所以"本窗口只接受第一张"这种**跨调用计数**它自己做不到 —— 但**不需要它做**：

- **封顶是规则**（`MatchRules.MaxPunishResponsesPerRound`），由**引擎在询问之前**就抑制超额报价；
- **接受与否是策略**，策略只需对"被问到的"那一次说 yes/no。

⇒ **当 `maxPunishResponsesPerRound = 1`（现行发行值）时，`Accept` 的语义自动就是"每窗口接受第一张"**，`FirstInRound` 不需要独立实现：

| 想要的立场 | 实现 | 前提 |
|---|---|---|
| `Never` | `DeclineAllPunishResponses` | 无 |
| `FirstInRound` | `AcceptAllPunishResponses` | **cap ≥ 1**（现行发行值 = 1） |
| `Always`（真·无限制） | `AcceptAllPunishResponses` | **cap = 0** |

**这条分层是对的，同时解释了一个乍看矛盾的现象**：`bracket-accept`（无条件接受）在 cap=1 下**并不是**"接受一切" —— 引擎已经把每窗口压到 1 张。⇒ 报告里引用 `bracket-accept` 时**必须同时标注当时的 cap 值**，否则上下界会被误读。它仍然有意义：**cap=1 下 accept 与 decline 之间的跨度，就是"每窗口要不要用掉那一次反打"的价值**，而不是"回环全开 vs 全关"。


⚠️ **同时必须新增一条契约测试**：证明"所选打法 → 注入的策略 → 对局中的响应行为"这条链是通的（否则我们会重复犯"改了但没接上"这个错 —— 本会话已经犯过一次：`balance.json` 加载器接好了 .NET 侧却漏了 Unity 侧）。


名字与定位刻意对齐现有四阵营的**设计意图**（见 `CARD_DESIGN_MODEL §3.4`、`DESIGN.md`）：

| id | 中文 | 玩法 | 权重要点 | 主要面向 |
|---|---|---|---|---|
| `aggro` | 速攻 | 尽早压低对方生命/破城，不恋场 | 伤害/打脸权重高；惩罚成本权重**低**；铺场权重低 | 烈焰 |
| `control` | 控制 | 先换场、保住载体，慢 | 换场与自身生存权重高；惩罚成本权重**高**（怕喂牌）；打脸权重低 | 古木 / 深海 |
| `combo` | 组合 | 服务一条胜利轴（机械：提交→上传→下载） | 推进胜利轴权重**最高**；生命周期动作强偏好 | 机械 |
| `economy` | 经济 | 手牌与惩罚预算保守，避免洪流 | 惩罚成本权重**最高**；打满惩罚预算就宁可结束回合 | 深海 |

**⚠️ 实现期更正（2026-09-11）：`economy` 的原措辞"抽牌/手牌优势权重高"是 IMPLEMENTABLE 不了的，我错了。**
广告里**没有效果列表**，快照里**只有计数**（`HandCount`/`DeckCount`），所以"这个动作会不会抽牌"**无法在不读卡牌数据的前提下算出来** —— 而"不派生规则"是硬不变量。
⇒ `economy` 因此实现为 **"保护手牌与惩罚预算"**（`spend_card` −100、`discard_cost` −100、`punish` −12 为全场最大量级、`end_turn` +40：宁可过牌也不吃洪流），**不是"把手牌做大"**。
**是否要让"抽牌"可被特征化？** 需要**契约变更**（在广告里带上效果摘要/幅度）。**我的裁定：暂不做。** 理由：为了一个特征去改已经冻结的动作契约，代价与收益不成比例；而且"经济"打法的直觉本来就更接近"别把预算烧光"，而不是"多抽两张"。
| `tempo` | 节奏 | 每回合最大化"当回合产出" | 单回合收益权重高；长线轴权重低 | 通用对照 |

**首批至少实现 4 套**（建议 `aggro` / `control` / `combo` / `economy`），`tempo` 作为第 5 套备选。

**验收要求**：5 套打法在同一牌组上的**行为必须可区分**（见 §6）。

### 4.1 ⚠️ 必修：**括号基线**（owner 2026-09-11 的质疑直接催生了这一节）

owner 的原话是「**我不知道你的测试结论对不对**」。这个质疑有一个我原先没堵住的口子：

> **4 套打法全是"我"设计的权重。** 它们给出的"区间"可能只是**我一个人的偏好所覆盖的窄带**，而不是真实玩法的包络。若所有打法都共享同一个盲点（例如都低估某张卡），矩阵会一致地得出错误结论，而且**看起来还很稳健**。

**对策：除了风格打法，必须同时跑两个"极端括号"**，它们不是风格，而是**边界**：

| id | 定义 | 作用 |
|---|---|---|
| `bracket-decline` | **拒绝一切**可选的降临/响应（＝现有 `--decline-punish` 口径） | 下界：把"惩罚回环"关到最小 |
| `bracket-accept` | **接受一切**可选的降临/响应（＝现有贪心接受口径） | 上界：把回环开到最大 |
| `bracket-first` | 退休前的硬编码优先级（＝现行发行默认） | **历史锚点**：让所有新数字都能与过去已发布的读数对齐 |

**为什么这三个能提升可信度而不是混淆**：本会话已经实测过它们的**效应量** —— 同一引擎下 `bracket-accept` 与 `bracket-decline` 之间，平均回合 5.7 vs 16.3、古木 9.7% vs 43.1%、深海 86.9% vs 66.4%。**这个跨度远大于任何单张卡的数值改动**，所以任何"某卡超模"的结论，都必须先通过"**在两端括号下都成立**"这一关，否则就是策略伪影。

**判定升级**：§5.2 的 `ORDER-STABLE` 只有在**风格打法 + 三个括号**全部一致时才算数。若只在风格打法内部一致、在括号下翻转，同样**不得**用于数值决策。

> **⚠️ 与实现对齐（2026-09-11 23:0x 修正）**：本节先前引入了第三个状态名 `ORDER-FRAGILE`，但 **§5.2 只定义了两个状态，实现（`build-output/pl-csim/Matrix.cs` 的 `Verdict(...)`）按 §5.2 实现为 `ORDER-STABLE` / `ORDER-FLIPS` 两态 —— 代码是对的，是我的文档自相矛盾。**
> 现**统一为两个状态**：`ORDER-STABLE`（所有参与者给出同一排序）/ `ORDER-FLIPS`（否则，并列出哪些参与者不一致）。
> "不一致只发生在括号之间"这类细分，通过 `Verdict` 返回的 **`disagreeing` 名单**读出，**不再新增状态名**。理由：状态名越多，越容易在写报告时人为挑选对自己有利的那个 —— 保持两态更不容易被误用。


### 4.1.1 实测修正（2026-09-11 23:0x）：**今天只有两个括号，不是一个"三个括号"的设计**

实现者实测并断言：**`bracket-first` 与 `bracket-decline` 在当前引擎上是同一配置，读数逐字节相同。**
原因正是 §3.5：`src\Adapters` 里**没有任何地方注入响应策略**（`MatchFactory.cs:64`），引擎自带的 `DeclinePunishResponsePolicy` 回退已经在"拒绝" ⇒ `bracket-first`（"注入空 = 现行发行配置"）与 `bracket-decline`（"显式注入拒绝"）**语义相同**。

⇒ **今天从括号维度只能得到 2 个不同读数（accept / decline），不是 3 个。** 这不是缺陷，而是 F32 缺口的又一个侧面证据。
**第三个括号什么时候才有意义？** 当发行运行时**开始接受响应**（即响应策略接线之后）—— 那时 `bracket-first`（空注入）会与 `bracket-decline` 分道扬镳。

**实现者的处理我认可**：它**没有**为了"凑出三个括号"而把 `bracket-first` 改成接受 —— 那会毁掉它作为"历史锚点"的意义。

### 4.1.2 `bracket-accept` 的上界是**有量**的，不是理论最大（PL 判断：**接受这个近似，不建第 4 个括号**）

实测：**120 个报价、120 接受、105 实际发动；15 个被接受但在准备阶段无法结算**（响应效果需要选目标，或惩罚被转化为"弃自己的牌"需要选牌）。这是它与 harness 既有 `RecordingPunishPolicy(accept:true)` 完全同形所致。

实现者提议再建一个"真·每张都能结算"的括号（通过 `CardTargetValidator`/`TargetPolicy` 填合法目标与弃牌 id）。**我的裁定：不建。** 理由：
1. **缺口是已知且已量化的**：15/120 = **12.5%** 的响应。而括号两端之间的差距是 **105 vs 0 = 100%**。用 12.5% 的已知近似换取"上界严格性"，不改变任何决策。
2. **它会变成一个不可比的新仪器** —— 我先前引用的 5.7/16.3 回合、古木 9.7%/43.1% 都是在这个近似下测的，换仪器就得重测全部历史点，代价远大于收益。
3. **它需要复制引擎的目标合法性判定到 AI 层** —— 那正是"AI 不得派生规则"这条不变量要防的事。

**触发重议的条件**：若矩阵显示某个结论**恰好卡在括号边界上**（即 accept 与 decline 给出相反判定），则这 12.5% 可能成为决定因素，那时再建第 4 个括号、并**明确标注它是新仪器、不与历史数字混用**。


### 4.2 诚实边界（关于"打法是否代表人类"）

- 本仓库**没有人类对局语料**，所以**没有任何一套打法有权声称"代表玩家"**。
- 因此矩阵的用途是**证伪**而非**证实**：它能否掉一个结论（"换打法就翻转 ⇒ 不可用"），但不能证明"某卡确实超模"。
- 真正的证实只能来自**人类试玩**。这一条写在这里，是为了防止后人把"矩阵稳健"误读成"设计已被验证"。

## 5. Harness 接入：从"一个点"变成"一个矩阵 + 区间"

- `build-output/pl-csim` 增加 `--playstyle <id>`，并且**每份报告必须盖 `playstyleId` 与权重哈希**（沿用现有的 `t1Mechanism`/`engineSha256` 那套 provenance 纪律 —— 本会话正是靠它抓到了"仿真高估 29%"）。
- 新增**矩阵跑法**：`playstyle × 牌组`，输出按阵营的**胜率区间**（min/median/max + 每套打法的值），而不是单点。
- 报告里必须能回答：**"换打法后结论是否翻转？"** —— 若某阵营的强弱排序在 5 套打法下不一致，则该排序**不可用于改数值**。

### 5.1 报告字段契约（强制，缺一即视为无效报告）

沿用并扩展本会话已验证的 provenance 机制（它抓到过"策略仿真高估 29%"和"对着旧 DLL 跑出假结果"两次事故）：

| 字段 | 含义 | 为什么必须有 |
|---|---|---|
| `playstyleId` | 本局双方各用哪套打法 | 跨打法数字混用是本项目最容易犯的错 |
| `playstyleWeightsHash` | 权重向量的哈希 | 防止有人改了权重却拿旧数字对比 |
| `engineSha256` | 就是现有那个 | 已抓到过一次"旧 DLL 冒充新结果" |
| `maxPunishResponsesPerRound` / `t1Mechanism` | 现有 | 同上 |
| `balanceJsonRead` | 现在恒为 `false`（harness 自供 `MatchRules`） | 提醒读者：**harness 不读 `data/balance.json`**，所以它测的是"显式传入的规则"而不是发行配置 |

### 5.2 矩阵输出（③ 的核心交付）

`--matrix` 跑 `打法 × 牌组`，每个阵营输出：

```
faction: machine
  aggro   34.2%   control  41.7%   combo  50.0%   economy 37.5%
  min=34.2  median=39.6  max=50.0   spread=15.8
  robustness: ORDER-STABLE / ORDER-FLIPS(<哪些打法间>)
```

**判定规则（写死，避免事后解释）**：
- **`ORDER-STABLE`**：所有打法下阵营强弱排序一致 ⇒ 该排序**可用于**数值决策。
- **`ORDER-FLIPS`**：至少两套打法给出不同排序 ⇒ 该排序**不得**用于数值决策，必须先把"哪套打法更接近人类实际打法"讲清楚。
- 单套打法内的**差值**（同一打法、改一个变量）始终比跨打法的绝对胜率可信 —— 这与本会话已确立的纪律一致。

### 5.3 卡牌调整的数据通路（owner 要的"更好的测试结果"）

光有阵营胜率不够 —— 那只能告诉我们"某阵营弱"，不能告诉我们"改哪张卡"。所以矩阵还要采**逐卡使用遥测**，并把三张表**按卡 id 连起来**：

| 表 | 来源 | 回答什么 |
|---|---|---|
| **A. 模型偏差** | `build-output/pl-cardaudit/out-of-band.csv`（越出 ±1.5 带的 54 张） | "**理论上**这张卡偏强/偏弱多少" |
| **B. 使用遥测** | 新增：每张卡在每套打法下的**出场次数 / 被提交 / 被下载 / 被降临发动 / 胜率贡献** | "**实际上**有没有人用它、哪套打法用它" |
| **C. 灵敏度** | 现有的内存卡池消融机制（`CatalogVariant`） | "**改动**它对阵营胜率影响多大"（如 `winParam 6→5` = +12.22） |

**三类可操作的结论（这是通路真正要产出的东西）**：
1. **死卡**：B 表里出场率≈0 且所有打法都不用 ⇒ 要么设计过窄，要么数据写错（例：`sea_kraken`/`machine_assembler` 可降临但 `punishEffects` 为空，已单独点过名）。
2. **窄卡**：**只有 1 套打法**用它 ⇒ 该卡只服务于一种玩法，属设计意图不清晰；结合 A 表偏差决定"改强让它通用"还是"承认它是窄卡并明确标注"。
3. **高影响卡**：C 表灵敏度高 **且** A 表偏差大 **且** B 表使用率高 ⇒ **优先调整**（三条独立证据同时指向它）。反之，A 表说它超模但 B 表没人用，则**先查为什么没人用**，不要急着削。

**明确不做**：不让 AI 直接产出"建议把 X 改成 Y"。AI 只提供**证据表**；改哪个数字是 owner/PL 的判断。理由：本会话已经三次证明"看起来该改的"未必是该改的（S1 密度上限被否证、古木封印不是主因、机械该修胜利条件而不是代价）。

### 5.3.1 ⚠️ 读数边界：逐卡遥测给的是**使用率**，不是**逐卡胜率**（防止过度解读）
实现的 `CardUsage` 字段已核对齐全：`Played / Committed / Pushed / Pulled / PunishActivated / RolledBack`、`WinsHolding`、`GamesWithFaction`、`GamesWonByFaction`、`DeckCopies`、`TotalUses`，含 CSV 导出与按打法合并。

**但必须写清它能回答什么、不能回答什么**：

| 能回答（直接用） | **不能**回答（需要反事实） |
|---|---|
| 这张卡**多久被用一次**（`TotalUses`，可用 `DeckCopies` 归一） | 这张卡的**逐卡胜率贡献**。`WinsHolding`/`GamesWonByFaction` 是**按阵营**统计的 —— 一张卡在牌组里，所以"持有它的胜率"就等于**该阵营的胜率**，不是这张卡的贡献 |
| 哪套打法用它、哪套不用（→ 死卡 / 窄卡判定） | "把它改强 X 会怎样" —— 那必须走 §5.3 表 C 的**内存卡池消融** |

**⇒ 硬规则：任何"某张卡胜率 62%"的说法都不要出现在报告里。** 逐卡的因果只能由**表 C（消融）**给出；表 B 只负责"有没有人用、谁在用"。
这也是为什么 §5.3 要求**三张表按卡 id 连起来读**，而不是拿任何单张表下结论。

## 6. 验收标准（红→绿 + 可证伪）

1. **不变量仍在**：新增测试证明任何打法返回的动作都**逐字段等于广告**（沿用 `EveryPacedSubmissionIsAnAdvertisedActionForwardedUnchanged` 的做法），且**特征函数不接触 `GameState`**。
2. **默认打法行为不变**：现 `AdvertisedActionPolicy` 的既有测试全绿；一批"同广告、同快照 → 同选择"的钉死用例保持不变。
3. **打法可区分**（关键）：构造若干**合成广告集**，断言不同打法在这些集上**做出不同选择**（例如只有"打脸 vs 换场"两选项时 `aggro` 选打脸、`control` 选换场）。**这是"多看几套 AI"能成立的前提**，必须直接断言，不能只靠跑对局。
4. **矩阵产出区间**：至少跑出 `4 打法 × 4 牌组` 的矩阵，报告每阵营 min/max，并明确标注"排序是否稳健"。
5. **确定性**：同种子同打法两次跑出**逐字节相同**的报告（沿用 SHA256 比对）。
6. **全量门禁**：当前 **695/695** 必须保持绿。

## 7. 非目标与风险

**非目标**：不做最强 AI；不做 MCTS/NN/RL；不改规则、不改卡牌数值；不做难度分级 UI（可后续）；不碰 Unity 编译（本环境无许可证）。

**风险与对策**：
| 风险 | 对策 |
|---|---|
| 多打法让读数更不可比 | 报告强制带 `playstyleId`+权重哈希；只引用**同一打法内**的差值，跨打法只引用区间 |
| 权重靠拍脑袋 | 先给一组**可解释的初值**，再用矩阵结果复核；**不启动 GA 进化**（本期不引入不可解释的权重） |
| 特征偷偷派生规则 | 特征函数单测 + "不得接触 `GameState`"的编译期/测试期约束 |
| 5 套打法只改名字不改行为 | §6.3 的合成广告集断言（不同打法**必须**在构造集上分歧） |

#### 5.4.3 什么事情**不会**因为矩阵而改变
