## A. 城堡（Castle）机制

**现状事实**：
- `docs/RULES.md` **没有**城堡玩法规则专章（§1 唯一核心胜利方式 = 击败对方统领）。
- `docs/CHANGELOG_CASTLE.md` 提到的"共享王城 HP60"是**原型实验**，未写入 RULES。
- `docs/SPEC.md` §2 把"Castle 完整平衡"列为 MVP 之外。
- RULES §9 仅一句：「王城被击破时，破城方自己的胜利计数设为至少 9」。

**要问的**：
1. 城堡是正式规则吗？还是已放弃/暂停？
2. 第一版 Unity 要不要做城堡？
3. 若这版不做，接口要不要为后续城堡预留（快照/事件如何表达"功能关闭"）？

**答案（DeepSeek A-E + 人类裁决 2026-08-14）**：城堡保留并写入 RULES 正式节。核心语义已定：**双方共用、中立、无攻击力、推荐初始生命 75**（数据 `royalCastleMaxHp=75` 已一致）；破城后破城方胜利计数设为至少 9（人类裁决：牌库循环胜利阈值 10）。目标模型：王城通过 `DAMAGE_CASTLE` action 结算，**非独立 target**。功能关闭表达仍保留技术方案：`snapshot.castle = null` / `{enabled:false}`。
状态：`已确认`（人类裁决 2026-08-14，mailbox L3495）

## B. 玩家动作类型

**现状事实**：
- RULES §5 玩家主动动作仅三类：伏击阶段**盖放伏击**；行动阶段**出牌 / 攻击**。
- RULES §2：惩罚牌**无法主动打出**（被动触发）。
- `CHOOSE_TARGET` / `ACTIVATE_PUNISH` / `USE_LEADER_ABILITY` 三个动作名在 RULES/SPEC 中**均未定义**。
- 领袖卡有 `activated_ability` 字段（RULES §11.2），但未定义对应的触发动作。

**要问的**：
1. 出牌/攻击时要选目标吗？"选目标"是出牌动作的其中一步，还是独立一步动作？
2. 惩罚只能被动触发（对方抽到惩罚牌且满足条件时立刻发动），还是玩家也能主动激活？
3. 领袖技能怎么触发？需不需要一个独立的"使用领袖技能"玩家动作？

**答案（DeepSeek A-E + 人类裁决 2026-08-14）**：
1. **CHOOSE_TARGET 是出牌/攻击动作的子步骤，不是独立动作**——不保留独立 CHOOSE_TARGET action。
2. **ACTIVATE_PUNISH 保持纯被动触发**，无主动激活动作（对方抽到惩罚牌且满足条件时立刻发动）。
3. **USE_LEADER_ABILITY 不进入 MVP**——91 张卡无任何 `activated_ability` 字段，是 RULES 中存在但数据中不存在的幽灵概念。
玩家主动动作集收敛为：盖放伏击 / 出牌（含选目标子步骤）/ 攻击 / 结束回合。
状态：`已确认`（人类裁决 2026-08-14，mailbox L3495）

## C. 目标类型（Targeting）

**现状事实**：
- RULES/SPEC **均未定义**目标类型枚举（敌方单位/敌方玩家/友方单位/己方领袖/城堡…）。
- RULES §8：「嘲讽」对方必须优先攻击嘲讽随从；「扰魔」不能成为咒文/惩罚效果的目标。
- RULES §3：惩罚条件示例「敌方随从 ≥ 2」暗示目标以敌方单位为条件。

**要问的**：
1. 一张卡的效果能指定哪些目标类型？（请给出完整清单）
2. 有没有"不能选己方/不能选自己"之类的目标限制规则？
3. 嘲讽、扰魔在选目标时如何参与判定？

**答案（DeepSeek A-E，已从数据归纳）**：目标类型枚举 **8 值**：`ENEMY_FACE / ENEMY_TARGET / ENEMY_MINION / ALL_ENEMY_MINIONS / ALL_FRIENDLY_MINIONS / FRIENDLY_MINION / ALL_MINIONS / SELF`。王城不占独立 target（用 `DAMAGE_CASTLE` action）。正交维度 = **侧 × 对象（随从/统领/本体/王城）× 范围（单体/全体）× 约束（嘲讽/扰魔/护卫）**。约束参与判定：嘲讽强制优先、扰魔不可选、护卫拦击。
状态：`已确认`（DeepSeek 2026-08-13 A-E 答案，mailbox L2796）

## D. 隐藏信息（可见性）

**现状事实**：
- RULES 只明确两点：统领**正面朝上**（公开）；伏击**盖放**。
- 手牌、牌库顺序的对手可见性**未定义**。
- SPEC 快照 schema 把双方 `hand/deck/discard/battlefield` 全量放进结构（数据结构携带完整状态，但未规定 UI 侧谁可见谁不可见）。

**要问的**：
1. 对手的手牌**数量**可见吗？
2. 对手的手牌**内容**可见吗？（如不可见，第一版是否只需回传"数量"）
3. 盖放的伏击牌，对手看得到正/反面吗？
4. 牌库顺序是秘密信息吗？

**答案（DeepSeek A-E + 人类裁决，Java UI 已如此实现，仅需条文化）**：对手手牌**数量可见、内容隐藏**；盖放伏击**仅显示数量与档位（普通/专注/封场）**；牌库顺序为秘密信息，任何形式到达 Unity = Gate 失败。
状态：`已确认`（人类裁决 2026-08-14，mailbox L3495）

## E. Buff 负值（确认项，RULES 已有条文）

**现状事实**：RULES §11.1 已明确：
- `amount` 可为负数（保留卡牌设计自由度）。
- HP/生命值：保持负数参与计算；全部伤害结算后若仍 < 0 则死亡。
- Attack/攻击力：clamp 到 0（攻击不能为负）。
- 持续时间/回合数：clamp 到 0。
- Cost/费用：clamp 到 0（最多免费）。
- `amount = 0`：视为无意义 buff 并报错。

**要问的**：以上是否就是最终规则？（DeepSeek 曾问过 Buff 负值，确认后即可闭环）

**答案（DeepSeek A-E 确认 + PL 裁定）**：RULES §11.1 即最终规则：`amount` 可为负；HP 负数参与计算、全部伤害结算后仍 <0 则死亡；Attack clamp 到 0；持续时间/回合数 clamp 到 0；Cost clamp 到 0。**PL 补充裁定 `amount=0`：按 fail-closed 处理——拒绝启动该 buff 并报错，不静默跳过**（RULES §11.1 原文"视为无意义 buff 并报错"）。
状态：`已确认`（DeepSeek A-E 确认 2026-08-13 + PL 裁定 2026-08-14）
